# ADR：方案评估与解释策略

- 状态：已接受
- 日期：2026-08-02
- 最后修订：2026-08-08
- 范围：Python 规划 Worker、completion v6、Java 任务事件持久化/API/SSE、Vue 行程详情

## 1. 问题

技术上可行的行程没有暴露稳定的质量评分、结构化风险和重要选择的可审计原因。自由格式的模型解释不可复现，且可能声称不存在于计划中的证据。质量元数据还需要在不改变完成事件 Schema 版本的情况下，经受消息解析、持久化、任务查询、SSE 回放和历史记录的考验。

## 2. 决策

成功的 create/replan 结果由 `PlanEvaluator` 在 completion v6 发布前评估。评估器是**基于规则的、只读的**，且没有 LLM 或 Provider 依赖。它接收冻结的规划命令和不可变的 `PlanningResult`；时间通过可注入的 clock 提供。

completion v6 的可选 `evaluation` 对象具有 `schemaVersion=1` 和独立的 `evaluatorVersion`（如 `rule-v1`）。这使得评分策略可以在不启用 completion v7 的情况下变化。新 producer 写入 evaluation；Java 和 Web 对缺失 evaluation 的历史 v6 事件保持读取兼容。

## 3. 评分

所有维度使用 0 到 100 的整数分数。总分为加权和，采用整数 half-up 舍入，确保 Python 和 Java 在 `.5` 边界产生相同结果：

- 约束满足度（constraint satisfaction）：30%
- 时间可行性（time feasibility）：25%
- 预算匹配度（budget fit）：15%
- 路线效率（route efficiency）：15%
- 兴趣匹配度（interest match）：15%

权重和 warning 阈值集中在 `evaluation/rules.py` 中。warning 不能是实质性分数风险的唯一可观察效果：扣除必须在加权和整数舍入后仍然可见。兴趣匹配度保持为文档基线，直到活动拥有可靠的类别标签。

权重与 warning 阈值集中在 `evaluation/rules.py` 中。warning 不能是实质性分数风险的唯一可观察效果：扣除必须在加权和整数舍入后仍然可见。兴趣匹配度保持为文档基线，直到活动拥有可靠的类别标签。

### 3.1 评分语义修订（2026-08-08，`evaluatorVersion` → `rule-v3`）

- **HIGH_DAILY_LOAD 按加权 workload**：`ATTRACTION`/`EXPERIENCE` = 1.0、`MEAL` = 0.5、`ARRIVAL`/`DEPARTURE`/`ACCOMMODATION` = 0.0、未知 kind（含 DEMO）按 1.0 计（防规避）；阈值 `weighted workload >= 5.0`。`DayStats.activity_count` 保留（仅用于解释说明，不再参与评分）。
- **换乘按 actual slack**（间隙 − 换乘时长）分级，warning 与扣分共享 `transfer_slack_minutes` 单一事实来源：`slack < 12min` → TIGHT_TRANSFER；`slack < 4min` → LOW_TIME_BUFFER（CRITICAL）。warning 只做分类，不产生独立 penalty，避免双重扣分。**扣分按单日聚合（B1_C35，2026-08-08 同一未发布批次内补充）**：每日互斥计数 `tight_only_count`（slack ∈ [4,12)）与 `critical_count`（slack < 4），当日有风险腿时 `raw = 10 + 5*tight_only_count + 10*critical_count`，`daily = min(raw, 35)`；顺序无关，单日单腿时与逐腿全罚等价（TIGHT 15 / CRITICAL 20），封顶后 score saturation 为设计行为，warning 仍逐腿完整输出。
- **高负载递增扣分**：−18 基础 + 每满档 +6（`18 + 6 * int(overload)`），单日封顶 −30（档位：5.0–5.99 → −18；6.0–6.99 → −24；≥7.0 → −30）。
- **权重不变**（30/25/15/15/15）；evaluation `schemaVersion` 仍为 2；completion 事件契约 v8 不变；Java 透传与 Web 展示不变。

## 4. 完成与失败边界

评估仅描述成功的、可行的计划。预算溢出、行程日期违规或未覆盖的固定安排产生结构化的 `DATA_QUALITY_ERROR` 并阻止完成。失败事件永远不包含 evaluation。`feasible=false` 在完成评估中是非法的。

## 5. Warning 与解释

Warning 使用稳定代码、严重级别、实体类型/ID、指标、实际值和阈值。解释是由计划事实支持的确定性陈述，如固定安排、必去地点覆盖、路线模式、Provider 回退和分组。只有当归一化地点名称及其完整时间窗口都与某个活动匹配时，固定安排才算"已覆盖"。原因不能凭空编造事实或调用 LLM。

Provider 回退 warning 和决策使用与 provenance 相同的源 Transit 标识。在 Java 持久化期间，显式 Activity 和 Transit 引用映射覆盖单活动天、受影响的重规划日期和未改变的重规划日期，然后才写入终态 JSONB 事件。因此，GET 任务响应和 SSE/`Last-Event-ID` 回放暴露相同的持久化标识。

## 6. 持久化与兼容性

evaluation 留在 `planning_task_event.payload` 中；不需要新的关系表或 Flyway 迁移。`PlanningTaskService` 将其读取为类型化响应数据。缺失/null 节点表示历史成功，返回 `null`；无效的存储 evaluation 快速失败，而不是被静默地当作历史数据呈现。

Web 仅对拥有行程的成功任务显示 evaluation。成功的历史任务显示明确的兼容性提示。失败/取消的任务不显示分数或历史提示。

## 7. 验证

仓库包含 9 个确定性基准场景：清洁真实数据、接近预算边界、估算 Transit、固定安排、高每日负载、长步行、混合 Provider 回退、紧张换乘，以及组合场景（高负载 + 紧换乘）。组合场景通过 `requiredDimensions` 显式断言各维分数，不允许依赖 N/A 归一化。运行器使用冻结 clock，检查分数范围以及必须出现/必须不出现的 warning 代码。

共享完成 fixture 同时被 Pydantic 和 Java 消费者解析；Parser、PostgreSQL API/SSE 和 Web 组件测试覆盖了跨语言边界。

## 8. 版本化与回滚

- evaluation 的 `schemaVersion` 和 `evaluatorVersion` 独立于 completion v6 的版本号。
- 评分策略变更（权重、阈值、新增 warning）递增 `evaluatorVersion`（如 `rule-v2`），不启用 v7。
- 评估假设变更（新必填字段、语义重新定义）递增 evaluation 的 `schemaVersion`。
- 缺失/null evaluation 继续作为历史成功读取；当前 Java parser 对未知 `schemaVersion` 快速失败，不会静默降级为 `null`。若未来需要“跳过未知版本”，必须先形成新的兼容决策并同步 parser 与契约测试。
- 用户编辑版本（`USER_EDIT`）和回滚版本（`ROLLBACK`）无关联 planning task 时不继承评分。
- 评分规则必须始终可重现：相同输入产生相同分数和 warning。

## 9. 修订（2026-08-07）：独立 Hard Validation、N/A 语义与双层结果

第 2–8 节的历史决策继续有效。本节记录后续修订，解决"可行性混入评分"与"五维必填"两个问题。

### 9.1 独立 Hard Validation

- 可行性判断从 Evaluator 中分离为独立 `Hard Validation` 层，产出 `Feasibility Report`，是"可执行"结论的唯一来源。
- Hard Validation 失败（重复 POI、跨日断档、端点缺失、预算越界、固定预约未覆盖、开放时间冲突、时长越界、餐饮缺失、安全换乘不足）进入修复、重规划或失败终态，**不产生成功版 PlanEvaluation**。
- 失败事件永远不包含 evaluation（原第 4 节保持不变）。
- 结构错误不得再通过体验评分获得高分：硬校验失败时不存在 98/100。

### 9.2 N/A 语义与权重归一化

- 维度不再强制"无输入也给分"：
  - 无兴趣偏好时 `interestMatch=N/A`。
  - 无预算约束时 `budgetFit=N/A`。
- 总分只在**适用维度**上重新归一化权重；不在 N/A 维度上惩罚或奖励。
- N/A 必须显式展示（UI 显示"未适用"），不能表现为 100 分。

### 9.3 硬规则与软体验边界

- Continuity 是硬门禁，不重复奖励"本来就必须正确"的结构。
- Duration 的上下界属于硬规则（超出即不合法）；接近 recommended 属于体验评价。
- 系统默认餐饮要求至少保留用餐时间；具体餐厅未解析作为明确警告。用户显式餐饮窗口是硬约束。

### 9.4 UI 双层结果

- 前端分开展示"行程可执行：已验证/待修复"与"体验评分"。
- 硬校验失败时任务 API/SSE 不携带成功 evaluation（原第 6 节历史行为保持不变）。

### 9.5 契约载体

- evaluation 对象随完成事件延续到 v8（v8 = v6 + 可选日程最小字段 `dayType`/`kind`/`timeFixed`），`schemaVersion`/`evaluatorVersion` 版本化规则不变。
- 历史 v6 事件继续按只读兼容解析；缺失 evaluation 返回 `null`。
