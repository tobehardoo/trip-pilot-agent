# TripPilot V2.1 产品与执行规划

> **版本**: V2.1 "旅行决策与执行闭环"
> **状态**: 未交付 — 本文是目标规划，不表示相关能力已经实现
> **日期**: 2026-07-27
> **依赖**: V2.0 发布加固完成（当前代码中未提交修改即为加固成果）

---

## 1. 版本定位

V2.0 使 TripPilot 成为一个可靠的旅行计划生成器。用户可以创建约束驱动的行程、查看真实规划进度、编辑活动、切换交通、比较版本、分享和导出。

V2.1 的目标是让 TripPilot 成为一个**旅行决策与执行工具** — 用户不仅能在行前规划，还能在旅行当天执行行程、应对变化、记录实际消费并形成真实反馈。

核心用户旅程：

```text
用户生成并确认旅行计划
  → 系统形成行前准备清单
  → 用户确认预约、门票、酒店和交通事项
  → 旅行当天进入今日行程模式
  → 系统展示当前活动、下一活动和建议出发时间
  → 用户完成、跳过或延迟活动
  → 天气、闭馆或时间变化触发风险提示
  → 用户选择重新规划当天剩余行程
  → 系统保留已完成和锁定活动，只调整未执行部分
  → 用户记录实际花费和体验
  → 系统形成预计与实际对比
```

## 2. 当前产品缺口

基于对实际代码库的审查（2026-07-27），以下 V2.1 所需能力全部不存在：

| 缺口 | 现状 |
|------|------|
| 活动执行状态 | `activity` 表无状态列，无完成/跳过/延迟概念 |
| 今日行程页面 | 不存在移动端执行页面或今日模式 |
| 行前准备清单 | 无准备项模型、无清单生成逻辑 |
| 实际消费记录 | 所有费用字段均为 `estimated`，无 `actual` |
| 当天剩余重规划 | 仅有 `LOCAL_REPLAN`（交通刷新），无执行中重规划 |
| 旅行反馈 | 不存在活动评价或旅行总结 |
| 实时风险复核 | 城市情报存在但无旅行中按 TTL 复核机制 |
| 当前位置跟踪 | 地图使用固定 POI 坐标，无设备 GPS |

**可复用的现有能力**：

| 能力 | 位置 | 复用方式 |
|------|------|---------|
| 不可变行程版本 | `itinerary_version` (V5) | 当天重规划创建 `IN_TRIP_REPLAN` 版本 |
| 局部重规划 | `LOCAL_REPLAN` (V15), `replan_service.py` | 扩展为支持当天剩余行程重规划 |
| 城市情报快照 | `PlanningContextSnapshot` (V22) | 风险复核复用事实快照和 TTL 机制 |
| 幂等基础设施 | `planning_task` (V4), `itinerary_rollback` (V22), `itinerary_edit_idempotency` (V27) | 当天重规划复用幂等模式 |
| SSE 进度推送 | `PlanningTaskEventHub` | 风险提示可复用 SSE 通道 |
| Vue Router + Pinia | `router/index.ts`, `stores/` | 新增今日行程路由和状态管理 |
| 消息契约版本化 | `contracts/messaging/` | 新增执行相关命令和事件 |

### P0-1：行前准备中心

规划完成后，系统自动生成行前准备清单。

**领域模型建议**：

```text
PretripItem
  - id: UUID
  - tripId: UUID (FK → trip)
  - type: enum (RESERVATION, TICKET, TRANSPORT, HOTEL, DOCUMENT,
                WEATHER, PACKING, SCHEDULE, INFORMATION_REVIEW, OTHER)
  - title: String
  - description: String
  - status: enum (TODO, IN_PROGRESS, COMPLETED, DISMISSED, EXPIRED, NEEDS_REVIEW)
  - dueAt: OffsetDateTime?
  - sourceFactId: String? (FK → guide_fact 或 city_intelligence)
  - sourceType: enum (OFFICIAL, COMMUNITY, USER)
  - reliabilityLevel: String?
  - required: boolean
  - completedAt: OffsetDateTime?
  - createdAt: OffsetDateTime
  - updatedAt: OffsetDateTime
  - version: int (乐观锁)
```

**清单来源规则**：

| 来源 | 可生成的类型 | 是否必须 |
|------|------------|---------|
| 官方预约事实（OFFICIAL, 预约类） | RESERVATION | 是 |
| 官方门票事实（OFFICIAL, 票价类） | TICKET | 是 |
| 到达/返程安排 | TRANSPORT | 是 |
| 住宿锚点 | HOTEL | 是 |
| 官方关闭/开放时间 | SCHEDULE | 是 |
| 天气预报 | WEATHER | 否 |
| 社区攻略（预约建议） | RESERVATION | 否（仅建议，标记 COMMUNITY） |
| 社区攻略（打包建议） | PACKING | 否 |
| 过期/待复核事实 | INFORMATION_REVIEW | 否 |

**关键规则**：
- 社区事实不能自动生成"必须预约"类强制事项，除非有官方来源佐证
- 准备项与来源事实关联，事实刷新后准备项状态可更新
- 用户可手动添加准备项（`sourceType = USER`）

**API 影响**：
- 新增 `GET/POST /api/trips/{tripId}/pretrip-items`
- 新增 `PUT /api/trips/{tripId}/pretrip-items/{itemId}`（更新状态）
- 行程生成完成时触发准备项自动生成

### P0-2：今日行程模式

面向手机浏览器的"今日行程"页面。重点不是展示完整多日规划，而是帮助用户执行今天的安排。

**前端新增页面**：
- `TodayTripPage.vue` — 今日行程主页面
- 路由：`/trips/:tripId/today`

**页面展示内容**：
- 当前日期和天气
- 当前活动卡片（大尺寸，突出显示）
- 下一活动预览
- 建议出发时间
- 距离和预计交通时间
- 交通方式（可一键跳转地图）
- 地址（可复制）
- 门票或预约提醒
- 今日预计费用 vs 实际费用
- 已完成/未完成活动数量
- 风险提示（如有）

**用户操作**：
- 完成活动
- 跳过活动（需选择原因）
- 延迟活动（设置新开始时间）
- 提前结束当前活动
- 锁定活动（不被重规划影响）
- 报告问题（关闭/排队/天气/疲劳）
- 请求重规划剩余行程

**关键架构决策**：
- 今日模式不依赖 SSE 长连接保持打开
- 页面刷新后从后端恢复执行状态
- 当前时间以服务端北京时间为准
- 当前位置由用户手动确认（第一版不使用 GPS）

### P0-3：活动执行状态

执行状态独立于不可变行程版本保存。

**数据库新增表** (建议)：

```sql
CREATE TABLE business.activity_execution (
    id UUID PRIMARY KEY,
    trip_id UUID NOT NULL REFERENCES business.trip(id),
    itinerary_version_id UUID NOT NULL
        REFERENCES business.itinerary_version(id),
    activity_id UUID NOT NULL,
    status VARCHAR(20) NOT NULL DEFAULT 'PENDING',
    actual_start_time TIMESTAMPTZ,
    actual_end_time TIMESTAMPTZ,
    skip_reason VARCHAR(60),
    user_note VARCHAR(300),
    created_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,
    version INT NOT NULL DEFAULT 0,
    CONSTRAINT uq_activity_execution
        UNIQUE (trip_id, itinerary_version_id, activity_id)
);
```

**状态枚举**：`PENDING | IN_PROGRESS | COMPLETED | SKIPPED | CANCELLED`

**关键规则**：
- 每次点击"完成活动"不复制完整行程版本
- 只有改变剩余计划结构的操作才创建新的不可变版本
- 执行状态跨版本保持：新版本创建后，已完成活动的状态保持不变
- 行程回滚后，执行状态如何处理需在 Phase 1 详细设计

### P0-4：当天剩余行程重规划

V2.1 核心能力。复用现有 `LOCAL_REPLAN` 架构，扩展为支持用户执行中调整。

**新增版本来源**：`IN_TRIP_REPLAN`

**重规划输入** (新增消息契约)：

```json
{
  "taskType": "IN_TRIP_REPLAN",
  "tripId": "...",
  "currentTime": "2026-08-02T14:30:00+08:00",
  "currentLocation": { "longitude": 113.26, "latitude": 23.13 },
  "completedActivityIds": ["..."],
  "inProgressActivityId": "...",
  "skippedActivityIds": ["..."],
  "lockedActivityIds": ["..."],
  "remainingBudget": 500.00,
  "mobilityAdjustment": "REDUCED",
  "weatherOverride": "RAIN",
  "userReason": "天气变化，体力下降"
}
```

**重规划规则**：
- 已完成活动不可改变
- 正在进行的活动默认锁定
- 用户锁定活动不可删除
- 固定预约不可随意移动
- 默认只修改当天剩余部分
- 不自动改变后续日期（除非用户明确选择）
- 新结果创建 `IN_TRIP_REPLAN` 不可变版本
- 版本差异解释此次变化
- 保留触发重规划的原因

**复用现有架构**：
- Java `PlanningTaskService.createReplan()` 模式 → 新增 `createInTripReplan()`
- Python `replan_service.py` → 扩展为支持当天重规划
- RabbitMQ `planning.replan` 路由 → 新增 `planning.in-trip-replan`
- JSON Schema → 新版本 `planning-replan-command`

### P0-5：实时风险复核

旅行当天按 TTL 复核高影响事实。

**复核优先级**：
1. 当日天气（最高优先级）
2. 景点临时关闭
3. 开放时间变更
4. 预约要求变更
5. 交通时间显著变化
6. 官方临时公告

**刷新策略**：
- 用户打开今日模式时触发后台异步刷新
- 天气：每 30 分钟可刷新一次
- 关闭/开放：每 60 分钟可刷新一次
- 交通：用户主动请求时刷新
- 部分失败时使用最后成功快照并标记 stale
- 用户可手动触发刷新

**风险提示规则**：
- 只有有效且新鲜的**官方**事实才能触发高强度风险提示
- 社区事实变化仅作为信息提示，不自动删除或调整活动
- 过期事实提示"信息可能已过期"

**复用现有能力**：
- `CityIntelligenceRefreshProcessor` — 复用刷新管道
- `PlanningContextSnapshot.freeze()` — 复用快照机制
- SSE 通道 — 推送风险提示

### P0-6：实际消费记录

用户可以记录旅行中的实际花费。

**数据库新增表** (建议)：

```sql
CREATE TABLE business.expense_record (
    id UUID PRIMARY KEY,
    trip_id UUID NOT NULL REFERENCES business.trip(id),
    date DATE NOT NULL,
    activity_id UUID,
    transit_leg_id UUID,
    category VARCHAR(30) NOT NULL,
    amount NUMERIC(12,2) NOT NULL,
    currency VARCHAR(3) NOT NULL DEFAULT 'CNY',
    note VARCHAR(300),
    occurred_at TIMESTAMPTZ,
    created_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,
    CONSTRAINT ck_expense_amount CHECK (amount >= 0)
);
```

**分类**：`TICKET | TRANSPORT | FOOD | HOTEL | SHOPPING | ENTERTAINMENT | OTHER`

**展示**：
- 今日预计 vs 实际费用
- 全程预计 vs 实际费用
- 分类对比
- 超预算提示

**关键规则**：
- 未知费用不能视为 0 元（NULL ≠ 0）
- 删除或修改费用记录需要明确权限

## 4. P1 产品范围

### P1-1：旅行反馈

用户对活动记录简单反馈：值得/一般/不推荐/太拥挤/排队过久/太累/时间不足/交通不便/费用过高/体验与攻略不符。

第一版不使用机器学习。仅通过确定性规则影响当前旅行剩余行程和下一次相似旅行的默认偏好建议。

### P1-2：旅行完成总结

旅行结束后生成基于真实数据的总结：计划完成率、跳过活动、实际 vs 预计费用、实际旅行节奏、用户反馈摘要。

总结统计由确定性代码生成，不依赖模型虚构。

## 7. 关键数据流

### 当天重规划流程

```text
用户在今日页面触发重规划
  → Java 冻结重规划上下文（当前时间、位置、完成状态、锁定活动、剩余预算）
  → 创建 IN_TRIP_REPLAN 规划任务（幂等键）
  → Outbox → RabbitMQ
  → Python Worker 消费
  → POI 召回、路线计算、排序
  → OR-Tools 求解（已完成活动作为固定约束）
  → 发布进度事件
  → 发布完成事件（含新活动和调整原因）
  → Java 消费
  → 创建新不可变版本（IN_TRIP_REPLAN）
  → 更新当前版本指针
  → SSE 通知前端
  → 前端展示新行程和差异
```

### 风险复核流程

```text
用户打开今日模式
  → Java 检查上次刷新时间
  → 超过 TTL → 触发异步刷新
  → Agent API → Provider（天气、POI 详情）
  → 与快照对比
  → 如有高影响变化 → SSE 推送风险提示
  → 用户确认 → 触发当天重规划
```

## 8. 关键状态机

### 活动执行状态

```text
PENDING → IN_PROGRESS（用户开始活动）
IN_PROGRESS → COMPLETED（正常完成）
IN_PROGRESS → SKIPPED（跳过，需原因）
PENDING → SKIPPED（未开始就跳过）
COMPLETED →（不可逆）
SKIPPED → PENDING（用户恢复）
```

### 重规划版本来源

```text
PLANNING_TASK（首次生成）
USER_EDIT（用户编辑）
LOCAL_REPLAN（交通刷新，V2.0）
ROLLBACK（版本回滚）
IN_TRIP_REPLAN（当天重规划，V2.1 新增）
```

## 12. 安全和隐私

- 所有执行状态和费用记录校验旅行所有权
- 当前位置只在必要范围内使用，不持续追踪
- 日志不暴露用户位置、凭据和完整私人信息
- 用户可以删除消费和反馈记录
- 分享页面不暴露私人执行状态和实际消费（除非用户明确选择分享）

## 13. 分阶段实施

```text
Phase 0：V2.0 冻结（提交加固代码、合并主分支、创建标签、更新维护文档）
Phase 1：执行状态基础（activity_execution 表、今日行程读取模型、页面恢复）
Phase 2：行前准备中心（pretrip_item 表、自动生成、状态管理）
Phase 3：当天剩余重规划（IN_TRIP_REPLAN 命令、Python 求解、新版本）
Phase 4：实时风险复核（TTL 刷新、stale 降级、风险提示、SSE 推送）
Phase 5：消费和反馈（expense_record 表、消耗对比、活动反馈、旅行总结）
Phase 6：验收和发布（E2E、CI、Compose、移动端验收、文档同步）
```

每个阶段的退出标准：
1. 代码实现完成
2. 对应单元和集成测试通过
3. 跨服务契约测试通过
4. 相关 E2E 通过
5. 数据库迁移验证通过

## 14. V2.1 退出标准

### 产品
- 用户能查看和管理行前准备项
- 用户能在手机页面查看今日行程
- 用户能完成、跳过和延迟活动
- 页面刷新后执行状态可恢复
- 用户能基于当前时间重规划当天剩余行程
- 已完成和锁定活动不会被重规划改变
- 天气和官方临时关闭变化能形成风险提示
- 用户能记录实际消费
- 系统能展示预计和实际差异
- 用户能提交活动反馈
- 旅行结束后能生成真实数据总结

### 架构
- 计划版本与执行状态职责明确
- Java 继续拥有用户业务事实
- Python 只消费冻结的重规划上下文
- 异步命令和结果幂等
- Redis 不保存唯一业务事实

### 测试
- Java/Python/Web 全量测试通过
- Flyway V1→V33 升级通过
- 契约校验通过
- 四条核心 E2E 通过
- Docker Compose 全链路验收通过
- 移动端关键页面经过浏览器验收
