## 概述

TripPilot 的规划工作流是异步的、阶段化的。用户创建规划任务后，Worker 通过多个阶段逐步生成行程，每个阶段产生进度事件，最终发布完成或失败事件。

本文档同时描述**目标 pipeline**（权威口径）与**当前/目标差异**，避免把目标误当作现状。

## 当前运行时进度阶段

Python Worker 当前按以下阶段顺序执行，每个阶段产生对应进度事件。共 10 个阶段，最大进度为 95%（`RESULT_PUBLISHING`）；随后的完成以独立完成事件收尾，不伪造 100% 进度：

```text
TASK_ACCEPTED        — Worker 接受任务（5%）
CONTEXT_VALIDATING   — 校验规划上下文（15%）
CITY_FACTS_LOADING   — 加载城市事实（25%）
POI_RECALLING        — 召回候选 POI（35%）
CANDIDATES_RANKING   — 候选排序（45%）
ROUTES_CALCULATING   — 计算路线（55%）
CONSTRAINTS_SOLVING  — 约束求解/骨架填充（65%）
KNOWLEDGE_RETRIEVING — 检索相关知识（75%）
RESULT_EXPLAINING    — 生成解释（85%）
RESULT_PUBLISHING    — 发布结果（95%）
```

> 注意：`COMPLETED` 不是进度阶段。进度停留在 95% 后由独立完成事件结束。Web 已以 `SUCCEEDED/FAILED/CANCELLED` 终态覆盖残留 progress；v1 Schema 已接受 producer 使用的 `RESULT_PUBLISHING`，并保留 `RESULT_PERSISTING` 供历史消费者兼容。系统不伪造 100% 进度。

## 目标规划 Pipeline

`Structured Constraints → Normalize & Freeze → Trip Skeleton → Fixed Anchors → Available Windows → Candidate Retrieval → Visit Duration Profiles → Activity Placement → Meal Placement → Transit → Hard Validation → Repair/Replan → Experience Evaluation → Persist Immutable Version → Completed`

职责边界：

| 组件 | 目标职责 |
| --- | --- |
| Java application/domain | 校验和冻结输入；拥有任务生命周期、幂等、不可变版本持久化及完成事务。 |
| Python planning pipeline | 构建骨架、组织候选、时长、活动、餐饮、交通、验证和有界修复。 |
| Optimizer / OR-Tools | 在已知窗口、锚点和时长范围内做组合选择与放置；不得创造事实或改变业务语义。 |
| Evaluator | 在 Hard Validation 通过后计算体验质量，不负责把不可行结果包装成成功。 |
| Provider | 提供 POI、路线、开放时间和可能的时长证据；不决定领域策略。 |
| Frontend | 收集一致约束、展示执行状态和行程，不伪造进度或可行性。 |

## 当前/目标差异

| 维度 | 当前实现 | 目标 |
| --- | --- | --- |
| 求解路径 | 逐日贪心容量填充（`planning_provider.py` 逐日调用 `plan_day`）；OR-Tools 是依赖项但未进入主路径 | 全局组合选择/放置以 OR-Tools 为目标，但只处理已知窗口、锚点和时长边界 |

## 规划流程详解

### 1. 任务创建

- 用户通过 Web 创建规划任务。
- Java 写 `planning_task` 和 `outbox_event` 在同一事务中。
- Outbox 发布 `planning-create-command-v3` 到 RabbitMQ。
- 任务状态初始为 `QUEUED`。

### 2. 任务接受

- Python Worker 消费 `planning.create.queue` 中的命令。
- 发布 `TASK_ACCEPTED` 进度事件。
- Java 消费首个合法进度事件后，将任务从 `QUEUED` 更新为 `RUNNING`；Worker 不直接修改业务任务表。

### 3. 上下文校验

- 校验日期、预算、住宿、必去地点、固定安排等约束的完整性和合法性。
- 加载冻结的城市情报快照。

### 4. POI 召回与知识检索

- 通过 Provider 搜索候选 POI。
- 从城市知识库检索相关攻略、事实和历史数据。
- 可信官方事实可以形成硬约束，社区或过期事实只能影响排序。

### 5. 候选排序

- 根据用户偏好（兴趣、预算、节奏等）对候选 POI 排序。
- 考虑评分、热度、距离等因素。

### 6. 路线计算

- 通过 Provider 计算 POI 之间的步行或驾车路线。
- 生成距离、时长、polyline 等数据。
- 行程加载时不自动生成交通编辑草稿；用户展开超长步行段进行审阅时，前端暂存推荐方式，仍需用户确认后才创建不可变版本。

### 7. 约束求解与骨架填充（当前）

当前主路径是**逐日容量填充**，非全局求解：

1. 按日类型分类确定每天的结构（到达日、普通日、离开日、全天活动日）。
2. 构建当天锚点（到达/离开/住宿/固定安排），计算弹性窗口。
3. 在窗口内填充候选活动，预留餐饮时间。
4. 生成当天行程并累计费用与警告。

**硬约束**包括：
- 必去地点
- 到返时间
- 预约时间
- 预算硬上限
- 锁定活动
- 固定安排覆盖
- 非允许类型的重复 POI
- 活动时间重叠

**软约束**包括：
- 偏好匹配
- 步行距离
- 行程节奏
- 预算期望

### 8. 结果解释

- 生成确定性的五维质量评分（详见 [PlanEvaluation ADR](../adr/方案评估与解释策略.md)）。
- 生成结构化风险和可核验决策解释。
- 硬约束违规转为 `DATA_QUALITY_ERROR`，不发布伪成功。

### 9. 结果持久化

- Worker 发布 `planning-completed-event-v8`（成功）或 `planning-failed-event-v2`（失败）。
- Java 消费完成事件，创建不可变行程版本。
- 失败事件不创建版本。
- 终态事件持久化到 `planning_task_event`，支持 SSE 回放和任务查询。

## 修复循环（目标）

硬校验失败不直接失败整个任务，而是进入有界修复：

```text
Hard Validation 失败
  -> 定位失败规则与修复原因（重复 POI / 跨日断档 / 端点缺失 / 时长越界 / 餐饮缺失）
  -> Bounded Repair：最多三轮；移动营业/last-entry/餐饮窗口、约束游玩时长、移除安全的重复可选 POI、刷新受影响日期交通
  -> 仍失败：缩小范围局部重规划
  -> 仍不可行：明确失败（NO_FEASIBLE_ITINERARY）或请求用户补充输入
```

修复只调整可调整项，不破坏锚点、固定安排和硬约束语义。详细规则见[行程真实性与旅行骨架](行程真实性与旅行骨架.md)。

## 规划失败场景

| 场景 | 错误码 | 说明 |
| --- | --- | --- |
| 约束不可满足 | `NO_FEASIBLE_ITINERARY` | 硬约束冲突，如预算不足以覆盖必去地点 |
| Provider 失败 | `PROVIDER_ERROR` | 真实 Provider 多次重试后仍失败 |
| 数据质量错误 | `DATA_QUALITY_ERROR` | 硬约束违规，不可持久化为可执行计划 |
| 内部错误 | `INTERNAL_ERROR` | Worker 内部异常 |

失败事件使用 v2 schema，携带安全 category、operation、retry count 和关联 ID。

## 局部重规划

- 用户可指定受影响日期范围发起局部重规划。
- 使用 `planning-replan-command-v1` 消息。
- 包含基线版本 ID 和受影响日期。
- Worker 只重新规划指定日期，保持其他日期不变。
- 结果创建新的 `REPLANNING` 版本。
- 局部重规划结果必须重新通过 Hard Validation（含跨日连续性），不因"只改几天"而跳过验证。

## 协作式取消

- Java 发布 `planning-cancel-command-v1` 到 RabbitMQ。
- Worker 在检查点响应取消信号。
- 不强杀进程，保持消息幂等。
- 取消后任务状态变为 `CANCELLED`。

## 任务状态机

```text
QUEUED -> RUNNING -> SUCCEEDED
                  -> WAITING_USER (PLANNING_REVIEW_REQUIRED)
                  -> FAILED
                  -> CANCELLED
```

状态转换不可逆，同一旅行只允许一个活动任务。持久化状态机保持稳定；`REPAIRING` 通过 progress v2 表达内部修复轮次，不扩张持久化任务状态机。`WAITING_USER` 是可达终态之一：review-required 事件将任务置为 WAITING_USER 并结束该任务的事件流（SSE 终止），后续用户操作走编辑/回滚/新规划而非原任务流转。

## 城市情报刷新

- 规划前执行 best-effort 城市情报刷新。
- `CITY_INTELLIGENCE_PLANNING_WAIT_TIMEOUT` 控制等待上限（默认 `PT2S`）。
- 超时/运行中记录 `CITY_INTELLIGENCE_REFRESH_PENDING`。
- 成功但行程日期没有可用天气记录 `CITY_INTELLIGENCE_WEATHER_UNAVAILABLE`。
- planning context 标为 stale 并保留诊断，不能伪造天气数据。

## 可靠性保证

- **Transactional Outbox**：任务创建和消息发布保持最终一致。
- **At-least-once 投递**：消费者幂等处理重复消息。
- **SSE 持久化**：事件持久化到数据库，支持 `Last-Event-ID` 恢复。
- **消费快照**：任务重试必须可复现，后续事实刷新不改变既有任务输入。

## 已知限制

- 规划前城市情报刷新是 best-effort，不阻断 Demo、远期行程或 Provider 暂时失败。
- 当前只验证广州、步行/驾车路线；公交和其他城市未纳入真实 Provider 证据。
- 当前主路径是逐日贪心填充，全局最优求解（OR-Tools）与全旅程骨架是目标而非现状。
- 普通景点已在单次规划任务内跨日去重，但酒店、枢纽、餐厅等允许重复类型尚未形成完整规则集。

## B6：权威 Feasibility 运行时门禁

- Worker 在 provider 生成结果后调用 standalone validator（reportId 由 command.event_id 经 uuid5 确定性派生，validatedAt=occurredAt）。
- VERIFIED → v9 completion（先运行 PlanEvaluator）；UNVERIFIED/NEEDS_REPAIR → review-required v1（不运行 PlanEvaluator，保留候选 itinerary 与报告）。
- 只有 VERIFIED completion 才创建/切换正式 itinerary version；Review Required 将 task 置为 WAITING_USER，仅保存候选预览与报告。
- Java 已接入：v9 completion 经 parser 校验（evaluation 必填、report status=VERIFIED、fingerprint 复算一致）后，在同一完成事务内创建 version、持久化 report 并将任务置为 SUCCEEDED；report 落库失败则整个完成事务回滚（V33 `business.itinerary_feasibility_report`）。
- 完成/审查的 task event payload 与 V33 报告行保持一致：PLANNING_COMPLETED 的 payload 携带与 `report_json` 深结构相等的 `feasibilityReport`（activity/transit 引用 remap 为持久化节点 ID）；PLANNING_REVIEW_REQUIRED 的 payload 携带 candidateItinerary 与报告（引用指向候选临时节点）。
- Task API（`GET /api/planning-tasks/{taskId}`）派生 latest outcome：SUCCEEDED 暴露 VERIFIED report（无 candidate）；WAITING_USER 暴露 UNVERIFIED/NEEDS_REPAIR report 与 candidateItinerary（无 evaluation）；QUEUED/RUNNING/FAILED/CANCELLED 均不暴露报告。malformed 终态 payload fail closed。
- SSE 事件流：PLANNING_REVIEW_REQUIRED 与 PLANNING_COMPLETED/FAILED/CANCELLED 同为流终止事件；WAITING_USER/SUCCEEDED/FAILED/CANCELLED 任务订阅后立即重放并关闭。事件 payload 来自 task_event DB，live 与 replay 结构一致，`Last-Event-ID` 断点续传，owner 隔离。
- 版本摘要（`GET /api/trips/{tripId}/itinerary/versions`）经单次 LEFT JOIN 嵌套 `feasibility: {status, reportId, validatorVersion, validatedAt, ...}`；历史无 report 版本显式返回 `feasibility: null`，不伪造 VERIFIED，也不返回完整 reportJson。
- Demo 缺证据时为 UNVERIFIED review（不是 failure）；v8 completion 不再由 producer 生成，Java runtime fail closed。

## B6W：前端权威结果状态机与刷新恢复

- 新增只读端点 `GET /api/trips/{tripId}/planning-tasks/latest`：最新任务发现（`created_at DESC, id DESC`），owner 隔离，无任务/非 owner 统一 404；页面刷新后用于发现没有版本归属的 WAITING_USER review 任务。
- 前端统一 outcome parser（`readPlanningTaskOutcome` / `readPlanningEventOutcome`）：Task API、SSE live、SSE replay 共用；`SUCCEEDED` 仅接受 VERIFIED report + evaluation（无 candidate），`WAITING_USER` 仅接受 NEEDS_REPAIR/UNVERIFIED report + candidate（无 evaluation）；其余组合（含 status/eventType 不匹配、缺失必填字段）一律 malformed，前端显示"规划结果无法安全读取，请重新规划"并清空 outcome，不刷新正式行程。
- 页面加载顺序：trip → current itinerary → version summaries → latest task；latest 为 review 时恢复 review 面板（正式行程保持不变），为 QUEUED/RUNNING 时恢复订阅，为 SUCCEEDED 且与当前版本 task 一致时才作为正式版本 report/evaluation；latest 404 表示无任务（当前版本 report 仍由版本链读取）。
- 新任务启动、手动取消、terminal failed/cancelled、流中断重试耗尽均清除旧 report/candidate/evaluation，避免旧面板残留。

## B8：编辑与回滚候选重验证

- `POST /itinerary/edits`、`/edits/commit` 与 `/rollbacks` 返回 202 PlanningTask；生产入口不再直接写正式版本。
- Java 在事务中冻结 candidate、当前 trip 约束、baseline、changed dates 与精确 N-1/N/N+1 impacted dates，并通过 outbox 发布 `PLANNING_CANDIDATE_VALIDATION_REQUESTED` v1。
- Worker 为 candidate 重建 TripSkeleton/ValidationInputs，复用 Hard Validation 11/11 与最多三轮 repair；VERIFIED 才发布 completion v9，其他状态发布 review-required v1。
- completion v9 在同一事务创建 USER_EDIT/ROLLBACK 不可变版本、写全新 feasibility report 并切 current；review 与 stale outcome 均不改 current。
- 回滚只复制历史内容，不复制历史报告；验证输入使用当前 trip 约束、当前 planning context 和当前 Provider 路由刷新。

## B9：规划输入与主动放置完善

- 所有规划入口（AMap create、Demo create、Local replan、repair 重投影、B8 EDIT/ROLLBACK）共用同一投影模块 `planning/validation_projection.py`，产生一致的 TripSkeleton/ValidationInputs。
- Demo：多日住宿 UNRESOLVED、不伪造酒店/坐标/POI ID/官方 evidence、meal 投影显式 UNAVAILABLE、保留用餐占位；缺真实证据时验证保持 UNVERIFIED。
- Replan/repair：从最终候选重建 skeleton/inputs，repair 不再复用旧 candidate 的 binding/locator；dayType/locked/provider metadata 不丢。
- Opening-aware 放置：仅 resolver 的 VERIFIED_WINDOW/VERIFIED_CLOSED 且 hard_constraint_eligible 的证据约束放置（最早合法窗口优先、last-entry 上限、确定性 tie-break）；VERIFIED_CLOSED 候选排除、must-visit 关闭日期标记 MUST_VISIT_CLOSED 不可行；AMap provider evidence 永不升级为硬窗口。
- 显式 meal window 优先默认建议；冲突产生 MEAL_WINDOW_CONFLICT 不静默丢餐；跨午夜窗口按 +1440 真实日期处理。
