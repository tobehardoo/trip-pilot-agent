## 核心设计原则

### 不可变行程版本（Immutable Itinerary Version）

每次修改行程都创建一个新的不可变版本，绝不覆盖历史版本。版本来源类型包括：

| 来源类型 | 说明 |
| --- | --- |
| `PLANNING` | 异步规划任务首次生成 |
| `REPLANNING` | 局部重规划 |
| `USER_EDIT` | 用户编辑活动或交通段 |
| `ROLLBACK` | 回滚到历史版本 |

版本号单调递增，回滚不修改历史版本，而是复制目标版本并创建新的 `ROLLBACK` 版本。

## 编辑模型

### 可编辑实体

用户通过 Web 界面编辑行程时，涉及以下可编辑实体：

- **EditableActivity**：活动的名称、地点、时间、备注等字段的修改。
- **EditableTransitLeg**：交通段的交通方式（`TRANSIT` 或 `TAXI`）、确认状态。
- **EditableDay**：某一天内的活动排序、添加或删除活动。

### 编辑草稿与确认

编辑操作分两步：

1. **暂存草稿**：多项调整先暂存为草稿，用户可以预览但不影响当前版本。
2. **确认提交**：用户确认后一次性创建新的不可变版本，所有草稿在同一事务中持久化。

### 编辑请求幂等

适用于 `POST /api/trips/{tripId}/itinerary/edits` 和 `POST /api/trips/{tripId}/itinerary/edits/commit`。两者必须提供 UUID 格式的 `Idempotency-Key`。

- 相同 key 且业务语义相同的请求返回首次生成的行程版本，不新增版本。
- 请求比较使用只包含编辑业务字段的确定性 SHA-256 指纹。
- 相同 key 与不同指纹返回 `409 IDEMPOTENCY_KEY_CONFLICT`。
- 历史记录中空白或 NULL 指纹同样返回该错误。
- 并发相同 key 由数据库唯一约束仲裁（`business.itinerary_edit_idempotency` 表的 `(trip_id, idempotency_key)` 唯一约束）。
- 并发不同 key 而基线版本相同，仍可能返回 `409 ITINERARY_VERSION_CONFLICT`。

### 编辑事务

编辑写入在 PostgreSQL 单事务内完成：

1. 先写入 `PROCESSING` 预留记录。
2. 逐个写入 Activity 和 Transit。
3. 任何一步失败都会回滚版本、子记录和幂等预留。
4. 成功后更新为 `COMPLETED` 和结果版本。
5. 故障解除后原 idempotency key 可成功重试。

## Typed Nodes 与骨架到版本的转换

行程内容由不同类型的节点组成，不同语义：

| 节点类型 | 语义 | 持久化 |
| --- | --- | --- |
| Anchor | 到达、离开、住宿、固定安排 | 行程版本中的活动/节点 |
| Activity | 放入槽位后的候选 POI | 活动 |
| Meal | 预留用餐时间的特殊节点；餐厅是后续绑定 | 当前以活动形态呈现 |
| Transit | 连接两个可执行节点，端点必须一致 | 交通段 |

**骨架到版本转换**：Python 规划期的 `Trip Skeleton` / `DayPlan` 是临时领域聚合，不等同于最终行程版本。版本化发生在硬校验通过之后——Skeleton 经验证并生成不可变行程版本，Skeleton 本身不持久化为"版本"。转换边界见[行程真实性与旅行骨架](行程真实性与旅行骨架.md)。

## 编辑后重新验证

本节描述目标规则。当前 `USER_EDIT`/`ROLLBACK` 版本不继承 PlanEvaluation，也尚未接入独立 Hard Validation；在该验证边界落地前，不得把编辑版本宣称为已经完成同等可执行性验证。

用户编辑会生成新的不可变版本，编辑后的版本必须满足与规划结果相同的硬规则：

- 编辑后重新执行 Hard Validation；失败不得持久化为"已验证"的可执行版本。
- **跨日修改影响范围**：修改某天的活动或交通可能破坏相邻日期的连续性（如把前一天最后一个活动移到无法到达住宿的位置）。影响范围必须扩展到受影响的相邻日期，而不只是被编辑的单日。
- 局部重规划结果同样重新验证（含跨日连续性），不因"只改几天"而跳过验证。
- 被破坏的跨日连续性是拒绝保存、标警告还是强制局部重规划，见[行程真实性与旅行骨架](行程真实性与旅行骨架.md)的"未决问题"。

## Transit 端点匹配

Transit 以活动端点对 `(fromActivityId, toActivityId)` 关联，而非数组下标。乱序合法，重复端点非法。持久化层会拒绝歧义源数据。

局部重规划中的 Transit 锁状态按源活动端点匹配，规避源存储顺序变化造成的错配。

## 局部重规划

用户可以指定受影响的日期范围发起局部重规划。系统使用基线版本和受影响日期，只重新规划指定范围内的活动，保持其他日期不变。

重规划通过 `planning-replan-command-v1` 消息触发，Worker 处理后发布新的 completion v8 事件，Java 消费后创建新的 `REPLANNING` 版本。

## 回滚

- 回滚不修改历史版本，而是复制目标版本的全部内容。
- 创建一个新的 `ROLLBACK` 类型版本。
- 版本号单调前进，回滚操作本身留有审计记录。
- 回滚使用幂等键，重复请求返回第一次产生的结果。

## 版本差异

版本差异通过比较两个版本的 Activity 和 Transit 列表计算。当前实现按天分别查询，存在数据量增长后的 N+1 风险（当前无性能回归证据）。

## Transit Snapshot

通勤段编辑将用户选择的交通方式写回后端，保存：

- `mode`：`TRANSIT` 或 `TAXI`
- 重新计算的距离、时长、费用
- Provider 元数据和计算时间
- `stale` 过期状态标记

## PlanEvaluation 与版本的关系

- 当前行程版本会恢复关联 planning task 的 evaluation。
- 用户编辑版本（`USER_EDIT`）和回滚版本（`ROLLBACK`）无关联 planning task，不继承评分。
- 旧版本或失败/取消任务保持 `evaluation = null`。
- 接口失败显示非阻断错误并支持原地重试。
- 并发保护覆盖跨行程、跨会话和离开后重开同一行程。

## 并发控制

- 同一旅行只允许一个修改行程的活动任务。
- 编辑请求携带期望当前版本号，版本变化时返回 `409 ITINERARY_VERSION_CONFLICT`。
- 跨行程和重开竞态受请求代次保护。
- 旧版本请求或旧编辑响应不得覆盖新工作区 itinerary/evaluation。

## 已知限制

- `ItineraryService.toItineraryResponse`、版本读取和差异计算按天分别查询活动/Transit，存在 N+1 风险。
- 历史不可表达 replan 只能标为未记录（completion v6 provenance 已覆盖新场景，但旧 `DEMO_ONLY` worker 的 replan 无法满足合法组合）。
