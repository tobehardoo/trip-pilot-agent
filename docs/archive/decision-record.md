# 技术决策记录

本文档记录 TripPilot 开发过程中的关键架构决策、背景和取舍。不记录「我们用了什么」，只记录「为什么选这个」。

---

## ADR-001: Java 作为业务后端而非 Node.js 或 Python

**日期**：项目启动时

**决策**：业务后端使用 Java 21 + Spring Boot 3。

**理由**：
- 核心业务（用户、旅行、行程版本）需要强类型、编译期校验和成熟的事务管理
- Spring Security + MyBatis + Flyway 组合是国内企业级开发中经过充分验证的技术栈
- 团队成员更熟悉 Java 生态的调试、部署和运维

**舍弃**：
- Node.js：缺乏与 MyBatis/Flyway 等价的数据层生态，事务管理不如 Spring 成熟
- Python 全栈：FastAPI 适合 API 服务但不适合复杂的业务事务编排和 ORM 映射

---

## ADR-002: MyBatis 而非 JPA/Hibernate

**日期**：项目启动时

**决策**：ORM 层使用 MyBatis。

**理由**：
- 行程版本查询涉及多表 JOIN 和复杂条件（版本比对、跨天引用），MyBatis 手写 SQL 比 JPA 的 JPQL/Criteria API 更可控
- 数据库特性（PostGIS 空间查询、pgvector 向量检索）需要原生 SQL
- 团队对 MyBatis 比 JPA 更熟悉

**舍弃**：
- JPA/Hibernate：自动 SQL 生成在复杂查询中难以优化，延迟加载在版本克隆中可能引发 N+1
- jOOQ：类型安全但学习曲线陡峭，V1 不需要

---

## ADR-003: Transactional Outbox 而非 CDC

**日期**：规划任务异步化时

**决策**：消息投递使用 Transactional Outbox 模式（定时扫描 + RabbitMQ 确认）。

**理由**：
- 保证数据库写入和消息发送的最终一致性，不需要分布式事务
- 定时扫描实现简单，容易调试
- V1 规模下几秒的投递延迟不影响用户体验

**舍弃**：
- Debezium CDC：需要额外部署 Kafka Connect，运维复杂度远超当前规模
- 直接在 @Transactional 中发 MQ：事务回滚时消息无法撤回

**未来**：如果规划任务量增长到每秒数十个，可以评估 CDC。

---

## ADR-004: RabbitMQ 而非 Kafka

**日期**：消息队列选型时

**决策**：异步任务使用 RabbitMQ。

**理由**：
- RabbitMQ 的 exchange/routing-key 模型天然适合命令/事件分发拓扑
- 任务队列（每个 task 一条消息、消费后 ack）是 RabbitMQ 的标准场景
- V1 不需要 Kafka 的日志流式处理和消息回溯能力

**舍弃**：
- Kafka：更适合高吞吐事件流，但 TripPilot 是任务队列场景，不需要分区和日志压缩
- Redis Stream：缺少死信队列和交换机的原生支持

---

## ADR-005: Python 规划 Worker 而非 Java 单进程

**日期**：智能规划模块设计时

**决策**：规划计算放在独立的 Python 服务中。

**理由**：
- OR-Tools 的 Python 绑定最成熟，社区案例最丰富
- pgvector 的 Python 客户端（psycopg + 嵌入模型）生态优于 Java
- 高德 API 调用、HTML 解析等脚本类任务在 Python 中更简洁
- Python 服务的独立部署和扩展不影响 Java 业务事务

**舍弃**：
- Java 单进程：OR-Tools 的 Java 绑定可用但文档和案例少；Python 的文本处理优势无法利用
- Celery：引入了额外的 Broker 依赖，aio-pika 直连 RabbitMQ 更直接

---

## ADR-006: 行程版本不可变

**日期**：行程编辑功能设计时

**决策**：每次修改（规划生成、用户编辑、局部重规划）创建新的不可变版本，不原地修改。

**理由**：
- 可审计——每个版本完整记录「谁在什么时间做了什么修改」
- 可回滚——回滚只需切换指针，不需要逆向计算差异
- 可比较——版本差异基于两份完整快照
- 规划可复现——Python Worker 持有的基线版本不会被并行修改覆盖

**代价**：每次修改要复制全部活动和交通段，存储量增加。但 V1 的行程规模（每个版本 ~30 个活动）下，存储开销可以忽略。

---

## ADR-007: Demo 模式作为正式运行模式

**日期**：Provider 设计时

**决策**：Demo Provider 不是「测试桩」，而是正式运行模式之一。

**理由**：
- 开源项目的新用户可能没有高德 Key，Demo 模式让他们可以体验完整流程
- CI 测试不消耗 API 额度
- 固定输入产生确定输出，适合 Agent 评测

**约束**：Demo 结果始终标记 `provider=DEMO`，前端明确展示「演示模式」。

---

## ADR-008: pgvector 而非独立向量数据库

**日期**：知识检索模块设计时

**决策**：语义向量检索使用 PostgreSQL 的 pgvector 扩展。

**理由**：
- V1 知识数据量（~50 个文档，~500 个片段）不需要 Milvus/Qdrant 的性能
- 运维一致——同一个数据库实例
- 向量检索结果可以直接 JOIN 文档元数据表

**未来**：如果城市数量增加到 10+ 且每个 200+ 片段，再评估独立向量数据库。

---

## ADR-009: 协作式取消而非强制杀进程

**日期**：任务取消功能设计时

**决策**：取消任务时 Java 发布取消命令，Python Worker 在下一个检查点响应。

**理由**：
- 强制杀 Worker 进程可能导致数据库写入不完整（一半的活动已插入）
- 协作式取消让 Worker 有机会清理状态（关闭数据库连接、ack MQ 消息）
- 已发出的外部 HTTP 请求无法强制取消（设置了超时上限），尊重这个现实

**代价**：取消有延迟（取决于当前计算阶段的长度）。对于 V1 的 10-30 秒规划周期，这个延迟可以接受。

---

## ADR-010: 单一 Agent 而非多 Agent 协作

**日期**：Agent 工作流设计时

**决策**：使用一个显式的 Pipeline 式 Agent，不引入多个互相对话的专家 Agent。

**理由**：
- 多 Agent 在旅行规划场景中制造了表面复杂度——POI 搜索、路线计算、约束求解不需要 Agent 间的语义协商
- 单 Agent 的状态机更容易调试、追踪和评测
- LLM 调用是成本最高、速度最慢的环节——减少 Agent 数量直接降低延迟和费用

**舍弃**：LangGraph 的多 Agent 模式。当前甚至不需要 LangGraph——规划 Pipeline 是确定性步骤，用普通的 Python 函数编排即可。

---

## ADR-011: 人工注册可信来源，而非全网自动发现

**日期**：2026-07-26

**决策**：V1.3 使用 Java 业务库中的可审核城市来源注册表。系统只抓取已注册、已审核且
启用的 HTTPS 来源；Python 复用现有 DNS 固定解析抓取器。

**理由**：

- “官网”身份属于业务信任决策，不能由模型或爬虫自行授予。
- 注册表可以审计来源、解析策略、刷新策略和启停历史。
- 广州、北京、上海的有限可信来源足以验证产品链路，不需要建设通用爬虫平台。

**舍弃**：搜索引擎自动发现、登录态抓取、绕过验证码和大规模城市批处理。

---

## ADR-012: 规划只消费冻结事实快照

**日期**：2026-07-26

**决策**：Java 在规划任务事务中冻结 `PlanningContextSnapshot`；Python Worker 不在求解
过程中抓网页或查询 Java 业务状态。Provider 刷新只影响之后创建的新任务。

**理由**：

- 同一任务重试可复现，来源随后变化不会产生漂移。
- 事实是否官方、是否过期和冲突如何处理均在任务创建时留下审计证据。
- Java 继续拥有旅行级业务事实，Python 只负责采集候选和确定性规划计算。

**代价**：规划开始前可能限时等待刷新；超时后必须携带 stale 诊断继续，而不是无限阻塞。

---

## ADR-013: 回滚创建新版本

**日期**：2026-07-26

**决策**：用户回滚时复制目标历史版本并创建新的 `ROLLBACK` 版本，绝不修改历史版本或
直接把当前指针指回旧版本。

**理由**：

- 回滚本身也是用户操作，必须在时间线和审计中可见。
- 后续编辑始终从单调递增的新版本开始，避免版本号倒退和并发歧义。
- 幂等键可以稳定返回第一次回滚产生的版本。
