# 故障排查

- 文档状态：生效中
- 负责模块：全部
- 最后更新：2026-08-09
- 当前事实来源：是

## Docker Compose 启动失败

1. 确认 Docker Desktop/Engine 正在运行。
2. 检查 `8080`、`9090` 及 `.env` 中数据库/中间件端口是否冲突。
3. 确认 `.env` 已从示例复制，密码和三个应用密钥不再是占位值且互不复用。
4. 检查可用内存，建议至少 8 GB。
5. 查看状态和日志：

```powershell
docker compose -f compose.prod.yaml --env-file .env ps
docker compose -f compose.prod.yaml --env-file .env logs <service-name>
```

## `knowledge-init` 失败

1. 确认 PostgreSQL 已健康。
2. 查看 `knowledge-init` 日志中的数据库迁移错误。
3. 检查 `knowledge/` 文件是否完整。
4. 如果是已有本地数据与迁移不一致，先备份需要的数据；只有确认可以丢弃演示数据时才执行 `down -v` 后重建。

## 规划任务失败或超时

1. 在页面或 `GET /api/planning-tasks/{taskId}` 查看终态、`errorCode` 和 `errorCategory`。
2. 查看 Worker 日志和 RabbitMQ 队列状态。
3. `DEMO_ONLY` 下确认知识初始化完成。
4. 真实模式下检查 Key、Host、配额和网络；先切回 Demo 判断问题是否属于第三方调用。

常见错误：

- `NO_FEASIBLE_ITINERARY`：约束无法同时满足，检查固定安排、必去地点和可用时间。
- `PROVIDER_ERROR`：真实 Provider 配置或调用失败。
- `DATA_QUALITY_ERROR`：输入或候选数据无法满足质量要求。

Hard Validation 仍在完善中；如果怀疑系统生成了未被拦截的开放时间、跨日或路线端点问题，应记录复现场景并按领域缺陷处理，不能把它当成已验证行程。

## SSE 进度停止

1. 刷新页面，客户端会使用 `Last-Event-ID` 恢复。
2. 检查浏览器 Network 中的 EventSource。
3. 检查 Java API 和任务查询结果。
4. 区分 95% 的 `RESULT_PUBLISHING` 进度与独立完成/失败事件；终态应覆盖进度态。

## 行程编辑冲突

- `409 ITINERARY_VERSION_CONFLICT`：刷新当前版本后重新编辑。
- `409 IDEMPOTENCY_KEY_CONFLICT`：相同幂等键被用于不同请求，应为新操作生成新键。

不要通过覆盖当前版本绕过冲突；行程版本需要保持不可变和可追溯。

## 真实 Provider 无结果

1. 确认确实需要真实数据；普通本地体验应使用 `DEMO_ONLY`。
2. `REAL_ONLY` 下确认 `AMAP_WEB_SERVICE_KEY`、QWeather Key/Host 和浏览器 Key 各自配置正确。
3. 检查 `PROVIDER_MODE` 与旧 `DEMO_MODE` 是否冲突。
4. 查看安全错误分类、重试次数和 Provider 控制台配额。
5. `REAL_ONLY` 返回明确失败是正确语义，不能要求它静默变成 Demo 成功。

## RabbitMQ 队列积压

```powershell
docker compose -f compose.prod.yaml --env-file .env ps agent-service
docker compose -f compose.prod.yaml --env-file .env logs agent-service
```

同时检查消息 Schema、死信队列、消费者状态和 Outbox dead 记录。重复发送完成消息不应创建多个版本。

## 数据库连接问题

1. 确认 PostgreSQL 容器健康。
2. 检查 `.env` 中的密码和端口。
3. 查看 Java 与 `knowledge-init` 的连接/迁移日志。
4. 不要在未确认数据用途时删除 Volume。

## Windows 问题

### JaCoCo 非 ASCII 路径

把 JaCoCo 数据文件显式指向 ASCII 临时目录。Linux CI 通常不受此问题影响。

### pytest 临时目录权限

```powershell
uv run pytest --basetemp=.pytest-temp-clean
```

## 诊断入口

内部诊断 API 需要 `INTERNAL_DIAGNOSTICS_TOKEN`，只应返回脱敏失败上下文并执行幂等重试。不要把 Token、完整 Payload 或 Provider 响应粘贴到 Issue 或文档。

## 本地恢复演练

| 场景 | 预期结果 |
| --- | --- |
| RabbitMQ 重启 | durable 队列恢复，消费者重新连接 |
| Worker 暂停后恢复 | 待处理规划消息保留，恢复后任务收敛 |
| Java Consumer 暂停后恢复 | 完成消息保留，恢复后只持久化一个版本 |
| Redis 清空 | 缓存丢失但 PostgreSQL 核心数据仍在 |
| 整栈重启 | 长期服务恢复，`knowledge-init` 成功退出 |
| 重复完成事件 | 不产生重复版本或重复终态 |

这些演练用于本地可靠性验证，不依赖 DNS、TLS、staging、registry 或外部告警平台。更多运行命令见[本地运行指南](本地运行指南.md)。
