## 项目简介

TripPilot 是面向国内自由行的约束驱动旅行规划系统。它将日期、预算、兴趣、必去地点、固定安排和交通偏好转化为可执行、可解释且可恢复的多日行程。

当前版本处于本地发布候选（RC）阶段，尚未完成生产环境发布。

## 产品定义：完整、真实、可执行的旅行计划

TripPilot 的核心交付物是**"完整、真实、可执行的旅行计划"**。这三点分别对应不同的系统职责，不能混为一谈：

- **完整（Complete）**：多日行程必须覆盖到达/离开、住宿、每天的游览与餐饮、活动之间的交通，以及跨日连续性——不能只是"一堆好看的景点"。缺少住宿语义、餐饮未保留时间或存在跨日断档，都属于不完整。
- **真实（Authentic）**：计划中的事实必须有可追溯来源。Provider 提供 POI、路线、开放时间和可能的游玩时长证据；推导（如日类型分类、游玩时长默认值）必须版本化并可解释；Agent/LLM 只能给出带来源和置信度的建议，不能无中生有。估计值必须明确标记为估计。
- **可执行（Executable）**：只有通过硬校验的行程才能被呈现为"已验证"。硬规则（重复 POI、预算越界、固定预约覆盖、路线端点、跨日连续、开放时间冲突、时长越界、餐饮窗口）全部通过，行程才可作为可执行计划持久化；失败进入修复、重规划或明确失败，而不是得到一个高分但不可行的版本。

**可执行性（能否完成并持久化）与体验评分（有效计划的软性质量）是两件不同的事。** 硬校验失败不产生成功的 PlanEvaluation，UI 也必须分开展示"行程可执行：已验证/待修复"与"体验评分"。

## 核心能力

- 用结构化约束创建旅行，以异步任务和 SSE 展示真实规划进度。
- 支持高德 POI、路线、Web 地图与无外部凭据的确定性 Demo 模式。
- 逐日容量驱动的骨架规划：日类型分类、到达/离开锚点、餐饮预留、固定安排与弹性时段填充（见[行程真实性与旅行骨架](../architecture/行程真实性与旅行骨架.md)）。
- 交通段编辑写回后端并生成新的不可变版本；时间空档不足的方式标记为"需要调整行程"而非静默不可用。
- 多项行程调整先暂存为草稿，只在用户确认后一次性创建不可变版本。
- 版本差异、回滚与默认折叠的历史版本面板，避免版本列表占满页面。
- 匿名只读分享、ICS 日历导出、支持中文的 PDF 导出。
- 旅行归档/恢复、筛选搜索、知识导入与来源/新鲜度证据。
- Prometheus 指标、健康检查、死信队列与受保护的诊断入口。

## 用户旅程

```text
注册或登录
  -> 创建旅行并填写日期、预算、兴趣、住宿、必去/避开和固定安排
  -> 导入攻略或刷新城市情报
  -> 创建规划任务并查看真实阶段进度
  -> 查看带时间、交通、费用、地图概览和事实依据的行程
  -> 编辑活动或交通，生成新的不可变版本
  -> 比较或回滚版本
  -> 分享只读链接，或导出 PDF / ICS
```

## 已交付能力

- 账号、旅行、约束、归档/恢复、分页筛选和用户数据隔离。
- 异步规划任务，Worker 产生真实阶段事件，Java 幂等持久化并通过 SSE 支持 `Last-Event-ID` 恢复。
- 高德和 Demo Provider 双模式；Demo 模式可复现，真实模式失败必须明确降级。
- 可信城市情报、用户攻略导入、事实新鲜度、证据快照和规划影响展示。
- 成功行程展示确定性的体验评分、结构化风险和可核验决策解释；不适用的预算/兴趣维度显示“未适用”并从总分权重中归一化排除，历史行程明确提示未启用评估。
- 逐日骨架规划：到达/离开锚点、日类型分类、餐饮预留、固定安排与弹性时段填充；游玩时长使用版本化的量级默认值（LIGHT/NORMAL/HALF_DAY/FULL_DAY）。
- 兴趣匹配已基于 POI 类别对用户偏好做真实打分；无偏好时为 N/A，而不是误记为 100（见[方案评估与解释策略 ADR](../adr/方案评估与解释策略.md)）。
- 行程版本不可变；编辑、局部重规划、差异和回滚都产生可追溯版本。
- 通勤段编辑写回后端，保存方式、距离、时长、费用、Provider 元数据、计算时间和过期状态。
- 匿名只读分享固定到某个行程版本，Token 只保存哈希并支持撤销、过期和限流。
- PDF 与 ICS 导出，PDF 使用可渲染中文字体并经过独立渲染验证。
- 受保护内部诊断入口、Prometheus 指标和生产 Compose 健康检查。
- 方案评估使用无 LLM 的确定性规则和版本化权重；完成事件中的结果会持久化并随行程实体 ID 重映射。
- 城市情报可组合 QWeather 当前天气、7 日预报、近期历史天气与 AMap 数据；QWeather 失败时按可用数据显式降级。
- 天气时间轴、地图日期筛选联动，选中日期在天气与地图之间保持一致。

## Demo 与真实 Provider

Demo 模式是正式支持的运行模式，用于本地体验、自动化测试和无 Key 环境。它必须清楚标记估算、缓存或降级结果。

真实 Provider 模式用于生产或接近生产的验收。服务端 Web Service Key、浏览器 Web JS Key、安全密钥和域名白名单必须分开配置；真实底图成功只能在最终浏览器域名中验收。

Provider 模式取值：

| 模式 | 说明 |
| --- | --- |
| `DEMO_ONLY` | 本地无凭据开发，不发起任何外部 Provider 调用 |
| `REAL_ONLY` | 生产默认模式，要求真实 Key，失败即失败 |
| `REAL_WITH_EXPLICIT_FALLBACK` | 仅在显式白名单允许时使用 Demo 降级 |

## 执行性与体验评分（目标）

目标行程结果由两层独立结论组成；当前实现仍由 `PlanEvaluator` 同时承担有限硬规则守门与五维评分：

1. **可执行性（Feasibility）**：硬规则校验结果，决定行程能否持久化为可执行计划。失败进入修复、重规划或明确失败，不产生成功评分。
2. **体验评分（Experience Evaluation）**：只评价已经通过硬校验的计划，衡量软性质量（时间舒适度、路线平滑度、预算贴合度、兴趣匹配、内容丰富度）。

详情见[行程真实性与旅行骨架](../architecture/行程真实性与旅行骨架.md)与[方案评估与解释策略 ADR](../adr/方案评估与解释策略.md)。

## 结果页信息架构

结果页已把“我的要求”置于顶部，并将“行程可执行：已验证”与“体验评分”分开展示。以下仍是完整目标层级；Typed Nodes、Sticky Map 和高级信息折叠尚未全部完成：

1. **Trip Header**：目的地、日期、人数、预算、状态、当前版本。
2. **Constraint Summary（我的要求）**：节奏、偏好、必去、住宿、到达、离开及满足状态；编辑入口打开共享 ConstraintEditor。
3. **Planning Status**：仅规划中展示；完成后消失或替换为紧凑的"已完成/已验证"状态。
4. **Execution & Experience**：可执行性结果优先（已验证/待修复），体验分数次之；N/A 明确显示"未适用"。
5. **Itinerary Workspace**：Timeline 为主，Sticky Map 为辅助。
6. **Day Header**：日期、天气、日类型、可用时长和当日摘要。
7. **Typed Nodes**：Anchor、Activity、Meal、Transit 使用不同语义展示。
8. **Plan Explanation**：说明约束响应、主要取舍和警告。
9. **Share / Export**：作用于明确的不可变版本。
10. **Advanced Intelligence**：攻略、来源、Provider、技术诊断和详细决策默认降低层级或折叠。

## 约束编辑统一

创建页与编辑页已使用同一个 `ConstraintEditor` 产品模型，只通过 create/edit mode 区分提交行为。预算、人数/类型、节奏、偏好、到返、住宿、必去/排除、餐饮窗口与行动能力共享字段定义、默认值、校验和空值语义。区域级选择仍由创建流程的目的地控件负责，不属于约束编辑器内部状态。

## 非目标

当前不做机票、火车票、酒店库存、支付、真实预订、多城市联程、多人实时协作、完整 PWA、国际化、Kubernetes 迁移或大型爬虫平台。

## 已知限制

- 当前重点是单城市自由行；不提供机票、火车票、酒店预订或支付。
- 规划主路径是逐日贪心容量填充；OR-Tools 是依赖项但尚未进入当前主求解路径，全局求解是目标而非现状（见[规划工作流](../architecture/规划工作流.md)）。
- 普通景点已在单次规划任务内跨日去重，但酒店/枢纽/餐厅等允许重复类型尚未形成完整规则（见[行程真实性与旅行骨架](../architecture/行程真实性与旅行骨架.md)）。
- 未选择酒店时已生成 Unresolved 住宿语义节点且不伪造 POI/坐标；完整 Area Estimated 状态与跨日连续性硬门禁仍未实现。
- Demo 费用和路线是明确标注的估算值，不代表实时供应商结果。
- 出发前仍应核验营业时间、预约和票价。
- 真实生产发布需要完成 HTTPS、Cookie 安全配置、Provider 凭据/白名单和日志脱敏复核。
- 真实 QWeather 专用 Host/Key、AMap 服务端 Key 和 Web JS 最终域名白名单尚未在 staging 验收。
- HTTPS、Secure Cookie、告警、备份恢复、回滚和至少 24 小时 soak 尚无部署环境证据。

## 外部发布前置条件

- HTTPS 终止可用，且 `REFRESH_COOKIE_SECURE=true`。
- 七类运行镜像均以批准的 registry `@sha256` 引用部署。
- `INTERNAL_DIAGNOSTICS_TOKEN` 使用强随机值，并区别于其他应用凭据。
- `PROVIDER_MODE=REAL_ONLY` 时提供真实 Provider Key 和对应域名/IP 白名单。
- QWeather Key 与控制台分配的真实 HTTPS Host 成对配置。
- 高德 Web JS Key、安全密钥和最终浏览器域名完成真实底图验收。
- 日志脱敏复核通过，确认不会记录 Token、Cookie、Provider Key、模型 Key 或完整攻略正文。

## 下一步

优先处理会影响可靠性或发布信心的事项：

- 建立"完整、真实、可执行"的独立 Hard Validation；当前重复 POI、活动重叠与 N/A 评分语义已先行落地。
- 从已落地的景点跨日去重和 Unresolved 住宿节点继续扩展完整住宿三态与全旅程骨架聚合。
- 行程编辑端点补齐幂等键，前端同步生成并传递。
- 四条核心浏览器 E2E 旅程稳定纳入 CI。
- 在历史消费者可淘汰后移除进度阶段别名；当前 95% 阶段、Schema 和 Web 终态覆盖已收敛。
- 旅行列表、行程读取和版本差异的 N+1 查询专项优化。
- 路由守卫、Windows CI、浏览器级 SSE 恢复和指标演练补齐。
