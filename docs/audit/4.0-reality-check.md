## 1. Executive Verdict

```
TripPilot = AGENTIC WORKFLOW（有边界的 Agentic Workflow，未到 Production Agent System）
```

**三个事实层：**

| 层 | 判定 | 一句话证据 |
|---|---|---|
| 外圈（对话/约束/决策/恢复循环） | **真 Agent 循环** | `decide → act → decide` 条件边（graph.py:639-645），决策器按 State 选择 9 个工具之一，观测回流 State |
| 内圈（行程生成/可行性） | **确定性 Pipeline（Agent 的 Tool）** | `build_itinerary` / `validate_itinerary` 是注册工具（tools.py:790-807），内部零 LLM |
| 双层之间的反射 | **部分断裂** | `Itinerary → Evaluation → State` 已通；`Evaluation → Next Decision` 只有"失败通道"，且 LLM 决策模式读不到结构化评估 |

**与用户假设的一致性（已证实）**：最大问题不是"没有 Agent"，而是——

```text
Agent → Planning → Evaluation →（断裂点）→ Next Decision
```

`Agent → Planning` 是通的（build_itinerary 工具）；`Planning → Evaluation → State` 是通的（plan_evaluation 进入 AgentState，tools.py:580-586）；**`Evaluation → Next Agent Decision` 只有半条腿**：结构化失败分类驱动确定性策略（RETRY/REPLAN/升级提问），但（a）质量信号从不参与任何决策；（b）LLM 决策器读不到 plan_evaluation 结构；（c）已记录的硬校验 FAIL 不阻止 EMITTED。

## 2. Agent Decision Authority（Audit A）

### A1 · Decision 是否真正决定下一步 Action？

追踪链（全部实测）：

```text
AgentState
  ↓ _decide_node (graph.py:652-664)
DecisionMaker.decide(state)  ── LLM: StructuredOutputDecider (graph.py:548-570)
                            └─ 规则: AskingDecider (graph.py:177-361)
  ↓ Decision(thought/call/answer/strategy) (graph.py:52-63)
pending_call / answer 写入 State (graph.py:657-663)
  ↓ _route (graph.py:724-731) 条件边
act (graph.py:666-722)
  ↓ ToolRegistry.invoke(call, state) (tools.py:830-850)
ToolResult → ToolObservation 追加 (graph.py:677-684)
  ↓ 失败分类 (graph.py:692-717) + plan_evaluation/extra 更新 (graph.py:684-685)
StateUpdate → 下一轮 decide
```

| 决策点 | 决策者 | 实际影响的代码路径 | 证据 |
|---|---|---|---|
| 下一步调用哪个 Tool | **决策器（LLM 或规则）** | `pending_call` → `_act_node` → `ToolRegistry.invoke` | graph.py:657-663, 666-676; tools.py:830-850 |
| 是否询问用户 | 决策器 | `ask_user` 工具 → `stop_reason=WAITING_USER` → `AGENT_ASK_USER` 事件 | tools.py:260-312; agent_processor.py:380-412 |
| 是否搜索/检索 | 决策器 | `search_place`/`get_route`/`check_opening_hours`/`retrieve_guide_knowledge` | tools.py:689-741 |
| 是否开始规划 | 决策器 | `build_itinerary` → `RealItineraryBuilder`/`DemoItineraryBuilder` | tools.py:790-798; itinerary_builder.py:216-240 |
| 是否 Retry | 决策器 | TRANSIENT 分支：同条件再 build 一次（≤1 自动 + 用户批准后） | graph.py:235-278; failure_policy.py:298-312 |
| 是否 Replan | 决策器 | 用户调整约束 → `update_constraints`（清除失败记忆/候选）→ rebuild | graph.py:190-234; tools.py:230-238 |
| 是否结束 | 决策器 | `answer` 非空 → `_route` → finish | graph.py:727-731 |

**结论 A1**：LLM/规则决策器**真实拥有**"下一步做什么"的选择权，且选择直接映射到实际执行的 Action。**不是"LLM Decision 是假的"。**

### A2 · Code Override Agent Decision 清单（Guardrail vs Override）

| # | 代码强制行为 | 位置 | 分类 | 判定 |
|---|---|---|---|---|
| 1 | LLM 提议的约束值必须 evidence-match 才 CONFIRMED，否则 INFERRED | tools.py:118-135, 192-210 | **Guardrail**（来源可证伪，防模型伪造） | ✅ 合理 |
| 2 | REJECTED 值禁止再次提议 | tools.py:189-191 | **Guardrail**（用户显式否定） | ✅ 合理 |
| 3 | 未知工具 → 强制回退 ask_user | graph.py:585-590; tools.py:838-842 | **Guardrail**（Tool 能力边界） | ✅ 合理 |
| 4 | 模型无 emit 工具；`validate_itinerary` 通过才自动 EMITTED | graph.py:718-721; tools.py:624-631 | **Guardrail**（确定性终态守门，fail-closed 哲学） | ✅ 合理 |
| 5 | 步骤/工具/LLM 三重预算上限 | graph.py:44-46, 655-656, 671-675, 549-553 | **Guardrail**（有界性） | ✅ 合理 |
| 6 | LLM 解析/传输失败 → 降级 AskingDecider | graph.py:562-569 | **Guardrail**（容错） | ✅ 合理 |
| 7 | LLM 决策从不看到 plan_evaluation 结构 / failure memory | graph.py:600-622 | **真实能力缺口**（不是安全理由，是反馈通道缺失） | ⚠️ 见 Q4 |

**结论 A2**：**不存在"Agent 决定 A、代码无理由强制 B"的架空式 Override。** 代码侧覆盖全部有明确安全/事实理由。真正的决策权缺口在 #7/#8——不是"被架空"，而是**信息通道缺失**。

## 4. Workflow vs Agentic Classification（Audit B）

按 7 项能力逐项评分（不以节点数/while loop/工具数量判断）：

| # | 能力 | 判定 | 证据 |
|---|---|---|---|
| 1 | State-driven Decision | ✅ | 决策完全由 AgentState 驱动（graph.py:652-664; 600-622） |
| 2 | Dynamic Action Selection | ✅ | 9 工具按决策选；LLM 自由生成 args；规则路径按槽位/失败状态选（graph.py:177-361） |
| 3 | Observation Feedback | ✅ | 观测追加 State + 进 LLM prompt + 进失败分类（graph.py:677-684, 621, 692-717） |
| 4 | Multi-step Loop | ✅ | decide→act 条件边循环，有界（graph.py:639-645; 44-46） |
| 5 | Adaptive Recovery | ⚠️ 部分 | 确定性策略：TRANSIENT 有界重试 / REPLAN / 重复失败升级提问（graph.py:235-278, 363-402）；**LLM 模式靠自由发挥，结构化分类不进 prompt** |
| 6 | Human-in-the-loop | ✅ | ask_user → WAITING_USER → AGENT_ASK_USER → AGENT_RESUME（tools.py:310; agent_processor.py:380-412, 234-320） |
| 7 | Resume Capability | ✅ | 每节点 checkpoint（graph.py:775-784; persistence.py:371-388）+ 生命周期（TTL/崩溃恢复，agent_processor.py:240-268） |

**分级**：

```text
Fixed Workflow ──→ LLM Workflow ──→ Agentic Workflow ──→ Production Agent System
                        ▲                  │
                        │                  └── TripPilot 在此 ◄──
                        └──── 无循环/无HITL/无Resume 的系统
```

**为什么是 Agentic Workflow（而非 LLM Workflow / Production Agent System）：**
- 不是 **LLM Workflow**：存在真实的 `State→Decision→Action→Observation→Decision` 多步循环、真实 HITL（WAITING_USER 中断）、真实 Resume（checkpoint v2 + 生命周期）。LLM Workflow 不具备这三者。
- 不是 **Production Agent System**：缺少"评估驱动的自主重规划"（无 Evaluation→Replan 路径）、决策器之间的能力不对称（LLM 读不到结构化评估/失败分类）、无 episodic plan memory 参与决策、Agent 不能自主修改行程内容（无 replan 工具，只能用户改约束后 rebuild）。
- 在**无 LLM 配置**时（factory.py:160-161），循环退化为**确定性策略的决策循环**（AskingDecider）——仍然是 decision loop，只是决策者是规则。这使其成为"双决策者 Agentic Workflow"。

## 5. Planning Pipeline Relationship（Audit C）

### C1 · Planning Pipeline 是 A/B/C 哪种？

**A. Agent Tool（真实后端）/ C. 绕过 Agent 的 Pipeline（命令路径）—— 两者并存：**

| 路径 | 关系 | 证据 |
|---|---|---|
| Agent 对话框内 | **A. Agent Tool**：`build_itinerary` 注册在工具集（tools.py:790-798），由决策器选择调用；`validate_itinerary` 是发射闸（tools.py:799-807） | 决策器决定 build；工具内部转发到确定性管线（tools.py:491-596） |
| MQ 命令路径（无 Agent） | **C. 绕过 Agent 的独立命令链**：`PLANNING_CREATE` → `process_planning_create` → provider.plan → 校验/修复 → 事件（processor.py:71-113, 191-295）；`PLANNING_REPLAN`/`CANDIDATE_VALIDATION` 同链（processor.py:116-182） | agent_processor.py 模块自述："Planning commands never enter this module"（agent_processor.py:1-9） |

判定：**管线本体是确定性 Workflow；Agent 通过 Tool 边界调用它，管线不是 Agent 内循环的一部分**（管线内无 Agent 决策点）。这不构成"Agent 不参与规划"——Agent 决定**是否**规划、**何时**规划、规划失败**怎么处理**；但规划**过程**与**结果质量**不归 Agent 管。

### C2 · 规划结果是否回到 Agent？

```text
Itinerary ──▶ _build_itinerary 写入 State:
                 candidate_itinerary (tools.py:580)
                 plan_evaluation     (tools.py:584)  ← 硬校验摘要 {status, failures[]}
                 decision_summaries  (tools.py:585)  ← 管线 DecisionTrace ≤12 条
                 goal                (tools.py:583)
   │
   ▼
PlanEvaluation（评分版，evaluation/models.py:151-204）
   只在 worker 路径生成: processor.py:280 (get_plan_evaluator().evaluate)
   ❌ 不进 AgentState —— Agent 拿到的只是硬校验摘要，不是 PlanEvaluation
```

**是否形成闭环？**

| 环节 | 状态 | 证据 |
|---|---|---|
| Itinerary → AgentState | ✅ | tools.py:580-586 |
| AgentState → DecisionMaker | ✅（字段级） | plan_evaluation 被失败分类读取（graph.py:692-706）；AskingDecider 读 failure memory 分支（graph.py:190-234） |
| **DecisionMaker → 基于 Evaluation 的 Replan/Retry/Accept** | ⚠️ **只有失败通道** | 结构性 blocker → FEASIBILITY 恢复（graph.py:296-312）；PLANNING_INFEASIBLE → 用户调整 → rebuild（graph.py:210-234）；**无"质量低→重规划"路径** |
| LLM DecisionMaker 读 Evaluation | ❌ | prompt 无 plan_evaluation（graph.py:600-622），仅观测文本摘要 |

### C3 · 真正缺失的是什么

**确实是「Planning Reflection Loop」缺失**，而非"Agent 不参与规划"。精确表述：

> Agent **参与规划触发**（工具调用）、**参与规划失败恢复**（失败分类 + 用户介入 rebuild），
> 但 **不参与规划结果评估驱动的下一步**：
> ① 发射判定不含评估（结构门通过即 EMITTED，graph.py:718-721）；
> ② LLM 决策器看不到结构化评估（graph.py:600-622）；
> ③ 没有任何代码路径把"评估差/硬校验 FAIL"转化为"重规划/再试/询问"——除非它是结构性 blocker。

### D3 · Evaluation Feedback Matrix

| Evaluation Result | Agent Reaction | Code Evidence |
|---|---|---|
| build ok + 结构门 pass | **EMITTED**（自动，无质量判断） | graph.py:718-721; tools.py:624-631 |
| build ok + 硬校验 FAIL（NEEDS_REPAIR） | **仍然 EMITTED**（若结构门放行）⚠️ 反事实实测：失败记忆 `USER_CONSTRAINT` 未解决与 EMITTED 并存 | graph.py:718-721（判据不含 plan_evaluation）；E0 反事实 S2 |
| build PLANNING_INFEASIBLE | 分类 USER_CONSTRAINT → ask_user（要用户调约束）→ 调整后 REPLAN rebuild | tools.py:519-540; failure_policy.py:133-137, 212-240; graph.py:210-234 |
| build 瞬时失败（TRANSIENT） | **RETRY 一次** → 再失败 ask_user（可批准重试） | graph.py:235-278; failure_policy.py:45-57, 298-312 |
| validate 结构 blocker | 分类 FEASIBILITY → 重复守卫 → 升级提问/停止 | graph.py:296-312, 363-402; failure_policy.py:250-253 |
| CAPABILITY_MISSING | 停止/移交（无询问） | graph.py:184-189; failure_policy.py:130-132, 317-319 |
| LLM 模式下任何失败 | 观测文本进 prompt，LLM 自由决定（无结构化分类输入） | graph.py:600-622 |

**结论 D1-D3**：Evaluation **不是纯展示**（失败通道真的驱动了决策），**但质量维度完全没有反馈**；且**失败通道在 LLM 模式下也不生效**（只记录、不进 prompt）。核心缺陷：**Agent 对"规划好不好"没有感知能力**——它只感知"规划有没有失败"。

| `astream` 值流快照（recorder 依赖） | 循环体本就在 `_decide_node`/`_act_node`，改成一个 `async` 生成器每步 `yield` state 即可等价复刻（约 20 行） |

**结论 F**：LangGraph 是**薄脚手架**（thin scaffold），不是 Agent 能力载体——**Agent 的一切实质（决策、工具、失败策略、checkpoint、HITL、Resume）都是手写的**。移除它不会失去任何 Agent 属性，但要重写 `run_agent` 的流式快照（约 20-30 行）。判定：**轻度过度工程，但非纯装饰**——`astream` 是真实依赖。建议保留现状（迁移成本 > 收益），但不该把"用了 LangGraph"当作 Agent 化的证据。

## 9. Failure Recovery Analysis（Audit G）

### 闭环追踪

```text
Failure
  ↓ ToolResult(error_code, data) (tools.py:35-46)
ToolObservation (graph.py:677-684)
  ↓ classify_failure：结构化证据（error_code / conflict_codes / reason_code）
     (failure_policy.py:164-260)
State Update: failure_kind / failure_signature / failure_attempts
     (graph.py:707-717)
  ↓
DecisionMaker 读 failure memory
  ↓
Next Action: RETRY / ask_user(调整→REPLAN) / escalate(提问或停止)
```

### 失败分类是否真正改变 Next Action？

| 分类 | 触发码示例 | 下一步行为 | 判定 |
|---|---|---|---|
| TRANSIENT | TIMEOUT/PROVIDER_UNAVAILABLE/RATE_LIMITED（failure_policy.py:45-57） | 有界重试 1 次 → 失败则 ask_user（graph.py:235-278） | **B. 改变 Next Action** |
| USER_CONSTRAINT | PLANNING_INFEASIBLE / 校验 reason（failure_policy.py:61-67, 71-83） | ask_user + 解析用户调整 → REPLAN rebuild（graph.py:190-234） | **B. 改变 Next Action** |
| FEASIBILITY | FEASIBILITY_BLOCKED（failure_policy.py:142-143） | 重复守卫 → 升级提问/停止（graph.py:296-312, 363-402） | **B. 改变 Next Action** |
| VALIDATION / CANDIDATE_EMPTY | 校验 reason / NO_RESULT（failure_policy.py:85-91） | 升级提问（graph.py:363-402） | **B. 改变 Next Action** |
| INTERNAL | TOOL_ERROR（failure_policy.py:113-127） | 停止（_STOPS_NOT_ASKS，failure_policy.py:317-319） | **B. 改变 Next Action** |
| CAPABILITY_MISSING | 未配置能力 | 停止/移交（graph.py:184-189） | **B. 改变 Next Action** |

**结论 G**：**在 AskingDecider（确定性策略）路径下，失败分类是 B——真正改变 Next Action**（RETRY/REPLAN/升级提问/停止五选一），且有重复预算防策略循环（failure_policy.py:304-312, 344-374；验收套件 A-H 已固化，tests/agent/test_decision_recovery_acceptance.py）。

**但存在模式不对称（关键发现）**：
- **LLM 模式（StructuredOutputDecider）下，失败分类只记录、不进 prompt**（graph.py:600-622 无 failure memory / plan_evaluation），恢复决策完全交给 LLM 读观测文本自由发挥，D-4 重复守卫被旁路。
- 即：**项目最精细的恢复机制只对"无 LLM"路径生效**——这与"LLM 是主决策者"的部署方向相反。
- 附带：AskingDecider 仅在 LLM 解析/传输失败时作为 fallback（graph.py:562-569），因此健康 LLM 模式下 D-2/D-3/D-4 全套策略实际不运行。

## 12. ONE Most Important Architecture Gap（Q4）

> **Planning Reflection Loop 缺失：评估（Evaluation）没有"回到"决策（Next Decision）的完整通道。**

精确含义（三合一，全部有代码证据）：
1. **发射判定不含评估**：`validate_itinerary` 结构门 4 项检查通过即 EMITTED（feasibility_gate.py:29-68; graph.py:718-721），硬校验 FAIL（NEEDS_REPAIR）不阻止发射（E0 反事实 S2）；
2. **LLM 决策器读不到评估**：prompt 无 plan_evaluation/failure memory（graph.py:600-622）；
3. **无质量→行为路径**：全代码不存在"Evaluation LOW → REPLAN/再试/询问"的任何分支（E0 Fact F）。

这不是"Agent 不参与规划"，而是**"规划结果无法反馈为下一步 Agent 决策"**——即用户假设的 `Agent → Planning → Evaluation` 断点，断在最后一段。
