## 1. 传输边界决策（本批前置）

**对话回合走 AMQP**（ADR-016）：`AGENT_START` / `AGENT_RESUME` 命令进 `trip.command.exchange`（新队列 `agent.dialog.queue` 消费），`AGENT_ASK_USER` 事件回发 `trip.event.exchange`；现网 HTTP dialog 通道保持不动至 P2.8。核心理由：回合时长有界但不紧凑，异步消除 HTTP 超时类失败；复用命令骨干（outbox/死信/幂等）；P1.8 契约与批次 B checkpoint/恢复机制由此获得生产调用方。Java 发布侧零改动（`RabbitPlanningCommandPublisher` 泛化接受任意 `OutboxEventRecord`，`agent.start` 路由键即用）。

## 4. 过程中发现并修正的问题

- **`AgentRunResult` 缺 `pending_options` / `pending_expected_type`**：`handle_start` 无法构造完整的 ASK_USER 事件（RED 测试抓到）。已补全——这是"运行结果应携带追问所需全部信息"的契约修复。
- 测试环境两课：`InboundMessageModel` 关闭按字段名构造（camelCase 关键字）；仓库无 pytest-asyncio（async 测试一律 `run_async` 同步壳）。

## 5. 语义细化与遗留

- **resume 重复投递语义**（批次 C 决策的落地细化）：worker 侧状态守卫（非 WAITING_USER 一律拒绝进死信）+ RESUME 审计 step；重复事件的 eventId 查重由 Java 消费方负责（与 planning 既有实践一致）。
- 能力注入：本批 `ToolRuntime()` 为空能力（工具 fail-closed）；真实 AMAP/可行性能力随 P2.2 接线。
- Java 触发端点与 ASK_USER 消费（落库 + SSE）分别归 P2.8 / P2.7；P2.5 intent 节点与 P2.6 critic 节点立项前须按审查报告三问论证。
