# 运行模型

- 状态：生效中
- 最后更新：2026-09-05
- 定位：本文件把散落在代码/ADR/方案里的**运行时模型**收敛为一页可查的权威摘要；细节以代码与对应文档为准。

## 1. 职责边界（Agent ↔ 确定性系统）

| 层 | 负责 | 不负责 |
|---|---|---|
| **Agent（有界会话）** | 意图理解、澄清提问、约束收集、策略判断、工具选择、冲突解释 | 不求解行程；不产出权威终态 |
| **确定性系统** | 约束校验、时间/预算/路线计算、候选→调度→硬校验、终态裁决（Finalize Gate） | 不做自由文本推理 |

权威行程只由确定性规划管线产生；`COMPLETED` 不等于真实成功，必须通过 `TRUE_SUCCESS_GATE`（状态 COMPLETED + 行程存在 + 天数>0 + 天数匹配 + 每日有活动 + 有效 POI + 前端真实渲染）。详见 [ADR：Agent 编排层与记忆系统](../adr/Agent编排层与记忆系统.md) 与 [Agent 化路线图](../product/Agent化路线图.md)。

## 2. Agent 运行模型（有界 LangGraph 循环）

```
User → Dialogue/Constraint Collection → Agent State → Strategy Decision
     → Tool Calling → Deterministic Planning Core → Validation → Finalize
```

- **Loop**：`decide → act → finish` 有界循环，默认确定性 `AskingDecider`（Level 2，无需模型密钥），配置 `STRUCTURED_MODEL_*` 后升级 `StructuredOutputDecider`（Level 3）。
- **State**：`AgentState` 持久化到 `agent.agent_checkpoint`（Postgres），单约束状态源；`dialog/` 只是该引擎的 HTTP 薄面。
- **工具**：声明式 `ToolRegistry`（build_itinerary / update_constraints / 等），工具结果以 `ToolObservation` 回填状态。
- **运行生命周期**：`RUNNING → WAITING_USER → COMPLETED / SUPERSEDED / EXPIRED / STOPPED / FAILED`（崩溃恢复 + 幂等 + TTL 过期）。
- **恢复/重试**：`failure_policy`（D-1 分类 → D-2 重试 → D-4 重复判定）；transient 类别派生自 `providers/errors.TRANSIENT_CATEGORIES`。

## 3. Planning 运行模型（确定性管线）

```
Constraint Normalization → Candidate Retrieval → Provider Enrichment
  → Feasibility Filtering → Scheduling/Optimization（贪心/启发式，可选 CP-SAT）
  → Transport Planning → Hard Validation → Itinerary Persistence
```

- 调度内核：默认贪心；`PLANNING_DAY_SCHEDULER=CPSAT` 可选精确（失败自动回退）；`SHADOW` 对照采样。
- 硬校验（`run_validation`）一票否决；不可行时输出冲突解释 → Agent 转述 → 用户调整 → Replan。
- 权威实现：`infrastructure/amap/planning_provider`（Facade + 6 协作者）+ `infrastructure/demo/*`（DEMO 模式）。

## 4. 数据流

```
Web (Vue3) ──HTTP/SSE──▶ Java travel-server ──Outbox──▶ RabbitMQ ──▶ Python worker
Python ──plan──▶ 确定性规划 ──PLANNING_COMPLETED──▶ RabbitMQ ──▶ Java 持久化 ──SSE──▶ Web
```

- 唯一契约源：`contracts/messaging/*.json`（Java/Python 双侧 fail-closed 校验）。
- 事件活跃集：PLANNING_COMPLETED v9/v10/v11、REVIEW_REQUIRED v1/v2、PROGRESS v1/v2、FAILED v1/v2、AGENT_* v1；旧代移入 `contracts/messaging/legacy/`。

## 5. 状态流

### 规划任务状态机（Java）

`QUEUED → RUNNING → WAITING_USER / SUCCEEDED / FAILED / CANCELLED`（`CREATED/RETRYING/CANCELLING` 为预留中间态）。

### 约束槽位五态（Python `SlotState`）

| 状态 | 含义 | 是否硬约束 |
|---|---|---|
| `UNKNOWN` | 未获得 | 否 |
| `INFERRED` | 推断（软偏好） | 否 |
| `CONFIRMED` | 用户陈述 | 是 |
| `USER_OVERRIDE` | 用户改写过已定值 | 是 |
| `REJECTED` | 用户显式否定 | 否（保留记忆，不再提议该值） |

只有 `CONFIRMED` / `USER_OVERRIDE` 可成为硬约束——fail-closed：宁可问，不猜测。

## 6. Constraint 模型

- 两层：`ConstraintSlots`（槽位+来源，运行时状态）与 `TripConstraints`（wire 契约，进入确定性管线）。
- 槽位名与 `TripConstraints` 对齐，填满的槽位集可直接投影到规划契约。
- 必填项：出行人数、预算在创建时必须提供，否则进入 COLLECTING 死锁（历史缺陷，已修：Java 网关透传 travelers/budget 到 TripContext）。

## 7. Failure-Recovery 模型

- **Provider 失败**：`providers/errors` 分类（TIMEOUT/NETWORK/RATE/QUOTA/...），`ProviderFallbackPolicy` 决定 real→demo 降级（配置门控）。
- **规划失败**：PLANNING_FAILED 事件 → Java 落 FAILED；`PlanningOutcomeGuard` 保证终态确定性。
- **不可行方案**：硬校验失败 → 冲突解释 → 用户调整 → Replan（`planning-replan-command`）。
- **恢复路径**：`failure_policy`（transient 重试、重复判定、WAITING_USER 恢复）。
- 关键纪律：fail-closed——数据不确定时显式 `UNKNOWN/UNRESOLVED/infeasible`，绝不伪造成功。

## 8. 代码规范要点

- Java/Python 服务间 JSON 一律 camelCase，trip 上下文走嵌套 `tripContext` 字段。
- 错误消息面向用户中文展示，不暴露 HTTP 状态码原文。
- 目的地/地点输入必须用地图索引选择，禁止自由文本。
- Python 侧 ruff（E/F/I/UP/B/SIM）为门禁；Java/Web 按既有分层与命名约定。
- 文档只描述真实存在的类/文件/事件/状态；发现过时即更新或删除。
