## 概述

本文档记录 TripPilot 的 REST API 语义、消息队列契约、SSE 协议和跨服务兼容规则。具体字段以后端类型、数据库迁移和 `contracts/` 中的 JSON Schema 为准。

## 消息契约版本策略

### 当前活跃契约

| 契约 | 方向 | 说明 |
| --- | --- | --- |
| `planning-create-command-v3` | Java → Python | 创建规划，包含完整约束和冻结城市情报快照 |
| `planning-replan-command-v1` | Java → Python | 局部重规划，包含基线版本和受影响日期 |
| `planning-cancel-command-v1` | Java → Python | 协作式取消 |
| `city-intelligence-refresh-command-v1` | Java → Python | 城市情报刷新 |
| `planning-progress-event-v2` | Python → Java | 当前进度事件；新增有界 `REPAIRING` 阶段与 attempt/action 统计，v1 历史只读 |
| `planning-completed-event-v9` | Python → Java | 当前成功事件；要求 VERIFIED FeasibilityReport 与 PlanEvaluation，Java runtime 仅接受 v9 |
| `planning-review-required-event-v1` | Python → Java | UNVERIFIED/NEEDS_REPAIR 候选，任务进入 WAITING_USER，不创建正式版本 |
| `planning-completed-event-v1`–`v8` | 历史/冻结 | v7 为 abandoned 草案；其余均不再由 Java runtime 接受为正式完成 |
| `planning-failed-event-v2` | Python → Java | **当前唯一新写入失败事件**，覆盖不可行、Provider 与内部失败 |
| `planning-failed-event-v1` | Python → Java（只读兼容） | 仅兼容历史 `NO_FEASIBLE_ITINERARY`，已废弃生产 |

### 嵌入式权威报告

| 契约 | 状态 |
| --- | --- |
| `feasibility-report-v1` | 已嵌入 completion v9 / review-required v1；当前 producer 使用 `hard-validator-v5`，VERIFIED 报告随完成事务持久化到 `business.itinerary_feasibility_report`（V33），v5 可携带最多三条 RepairAttempt |

### 版本兼容规则

- 消息必须包含 `schemaVersion`。
- 新增可选字段保持向后兼容。
- 删除必填字段或改变字段语义需要升级主版本。
- 旧版本 Schema 保留在仓库作为历史参考，代码只处理活跃版本。
- Demo 模式和真实 Provider 模式使用同一契约，不能使用前端模拟进度代替 Worker 事件。

### `PLANNING_COMPLETED` 版本状态

- **v9**：当前唯一运行时成功事件。Python producer 写入 VERIFIED report 与 evaluation；Java parser/service 双层 fail closed 并原子持久化正式版本与报告。
- **v1–v6、v8**：冻结历史版本，Java runtime 不再据此创建正式版本。
- **v7**：ABANDONED，未进入生产。`planning-completed-event-v7.schema.json` 仅作历史草案保留，不启用，其内容（transit cost/mode）不并入 v8。
- v6 可选 `providerProvenance` 是向后兼容扩展；历史 v6 无该字段时仍合法且表示"未记录"（v8 沿用）。
- v8 的 Transit wire 字段仅包含端点索引、`WALKING|DRIVING`、距离、时长、provider、estimated 与 polyline（与 v6 相同）。

### v6 起源、由 v8 承袭的 providerProvenance

- `actualProviders` 非空且与最终 Activity/Transit 来源一致。
- 非法 mode/provider/fallback 组合被 Schema 或模型/parser 拒绝。
- 历史 v6 缺失 provenance 仍可读取，消费者不得从顶层 provider 或子项来源补造 mode/fallback。
- Route operation 以稳定消息 ID 关联 Transit/Activity，Java 在完成事务内重映射为版本数据库 UUID。

### v6 起源、由 v8 承袭的 evaluation

- 当前新事件使用独立 `schemaVersion=2` 和 `evaluatorVersion=rule-v2`；`schemaVersion=1` 仅作历史只读兼容。
- v2 允许 `budgetFit`、`interestMatch` 在约束不适用时为 `null`；总分只按适用维度归一化权重，并采用整数 half-up 舍入。
- v1 仍要求五个维度全部为整数，解析器不得把历史缺失值改写为 N/A。
- create/replan 的新成功事件均携带 evaluation。
- 历史 v6 缺失/null 时任务 API 返回 `null`，failure 事件不携带该字段。

### 进度阶段与完成事件的边界

进度事件与完成事件是两条独立通道，不混为一条流水线：

- Python 进度阶段最大进度为 `RESULT_PUBLISHING`（95%）。`COMPLETED` 不是进度阶段。
- 完成通过独立 `planning-completed-event-v9`（成功）、`planning-review-required-event-v1`（需确认）或 `planning-failed-event-v2`（失败）事件收尾。
- Java 在消费完成事件的同一事务中持久化不可变版本；进度事件持久化与完成事务分离。
- 重连回放（`Last-Event-ID`）与任务查询暴露一致的终态字段；进度事件只按 sequence 单调回放。

### 当前进度契约状态

进度 producer、Schema 与展示终态已经完成最小收敛：

| 层 | 当前事实 |
| --- | --- |
| Python producer | 恒写 schema v2；repair 时可重复发送序号递增的 `REPAIRING`，之后发送 `RESULT_PUBLISHING`（95%） |
| `planning-progress-event-v2.schema.json` | 当前 producer 版本；接受 `REPAIRING` 与有界统计，并保留既有阶段 |
| Java / Web consumer | 同时接受历史 v1 与当前 v2；v1 禁止 REPAIRING，v2 的 repair statistics 严格有界 |
| Web 展示 | `SUCCEEDED/FAILED/CANCELLED` 终态优先，终态后不再展示残留 95% |

**现行规则**：终态事件覆盖进度态。任务达到 `SUCCEEDED/FAILED/CANCELLED` 后，前端停止播放或隐藏进度并呈现终态结果；不得通过伪造 100% 修复 UI。后续只在确认无历史消费者依赖后淘汰 `RESULT_PERSISTING` 别名。

## REST API

### 资源分组

| 分组 | 用途 |
| --- | --- |
| Auth | 注册、登录、刷新、登出和会话恢复 |
| Trips | 旅行创建、读取、约束更新、搜索、分页、归档和恢复 |
| Planning Tasks | 创建规划、创建局部重规划、取消、读取状态和订阅事件 |
| Itinerary Versions | 当前行程、版本列表、版本差异、回滚和活动/交通编辑 |
| City Intelligence | 来源注册、刷新、事实、冲突和规划快照 |
| Guide Intelligence | 公开 URL、正文、TXT/Markdown 和分享正文导入 |
| Shares | 创建、读取、撤销和过期匿名只读分享 |
| Exports | 固定行程版本的 PDF 与 ICS 导出 |
| Diagnostics | 受保护失败任务诊断和安全幂等重试 |

所有用户私有资源必须通过所有权校验；匿名分享只读取分享 Token 指向的不可变版本。

### 认证

- Access Token 使用 JWT，适合普通 API 请求。
- Refresh Token 使用 HttpOnly Cookie，并在刷新时轮换。
- 本机 HTTP 使用 `REFRESH_COOKIE_SECURE=false`；如果未来通过 HTTPS 公开访问，则必须改为 `true` 并重新评估会话安全配置。
- 内部服务调用和诊断入口使用独立强随机令牌，不复用用户凭据。

### Provider 来源与降级

- `PROVIDER_MODE` 取值为 `DEMO_ONLY`、`REAL_ONLY` 或 `REAL_WITH_EXPLICIT_FALLBACK`。
- 行程、Activity 和 Transit 均保留 `provider` 字段；路线还保留 `estimated`、距离、时长和 polyline。
- 只有 `provider=AMAP` 且 `estimated=false` 的记录才可作为真实 AMap 路线证据。
- 局部 route fallback 的成功结果顶层为 `MIXED`，目标 Transit 为 `DEMO/estimated=true`，其他来源保持 `AMAP`。

详细 Provider 降级策略见 [Provider 集成](Provider集成.md)。

### 错误响应

错误响应保持稳定结构：

```json
{
  "code": "ITINERARY_VERSION_CONFLICT",
  "message": "当前行程版本已变更，请刷新后重试",
  "details": {}
}
```

常见状态：

- `400`：请求格式、字段范围或业务约束非法。
- `401`：Access Token 缺失或过期。
- `403`：无权访问资源或诊断令牌无效。
- `404`：资源不存在或不属于当前用户。
- `409`：幂等键复用、版本冲突或活动任务冲突。
- `429`：限流，客户端应遵守 `Retry-After`。
- `500/502/503`：服务端或 Provider 暂时失败。

## SSE 协议

规划事件持久化后通过 SSE 推送给浏览器。浏览器断线后使用 `Last-Event-ID` 恢复遗漏事件。

每个进度事件至少包含：

- `stage`：标准阶段名。
- `sequence`：任务内单调递增序列。
- `progress`：阶段边界进度。
- `message`：用户可见状态。
- `occurredAt`：事件发生时间。
- `taskId`：任务标识。
- `statistics`：可选非负整数统计。

重复或乱序事件不得导致进度倒退；任务终态后前端停止继续播放该任务。终态集合包含 `PLANNING_COMPLETED`、`PLANNING_FAILED`、`PLANNING_CANCELLED` 与 `PLANNING_REVIEW_REQUIRED`（WAITING_USER 也是 SSE 终止状态）。

终态失败事件可返回 `errorCode`、`errorCategory`、`retryable`、`provider`、`operation`、`retryCount`、`fallbackAttempted`、`fallbackSucceeded`、`safeMessage` 和可选 `safeProviderCode`。成功终态可返回 requested/primary/actual providers、fallback reason、结构化 operations、`evaluation` 和 `feasibilityReport`。字段来自已持久化 task event payload，重连回放与任务查询语义一致。

## B6：权威 Feasibility 门禁事件

- **planning-completed-event-v9**：schemaVersion=9，payload 含 `feasibilityReport`（复用 feasibility-report-v1 语义）与 `evaluation` 两个独立字段；语义约束 status=VERIFIED、missingRequiredRuleIds 为空。Java parser 已接入：校验 report 类型、status、schemaVersion 与 itineraryFingerprint（跨语言 SHA-256 复算一致），VERIFIED 报告随完成事务原子持久化到 `business.itinerary_feasibility_report`（V33）。同一报告的 JSON 也写入 PLANNING_COMPLETED task event payload（`feasibilityReport`），与 V33 `report_json` 深结构一致；报告内 activity/transit 临时引用在持久化前 remap 为持久化节点 ID。
- **planning-review-required-event-v1**：schemaVersion=1，payload 含 status=WAITING_USER、候选 itinerary 与 `feasibilityReport`；语义约束 status 只能 UNVERIFIED/NEEDS_REPAIR，禁止 VERIFIED，且不携带 evaluation。Java 已接入 parser 与消费链（Rabbit `planning.review.queue` → `PlanningReviewService`，任务置为 WAITING_USER，不创建版本、不改 current version）；review task event payload 保留 candidateItinerary/knowledge/factImpacts/providerProvenance/feasibilityReport 供 Task API 与 SSE 读取。
- 规则报告中的受影响实体引用使用 typed refs（v4）：`activity:`/`transit:` 前缀指向活动/交通节点（完成落库时 remap 为持久化 UUID），`poi:` 保留 Provider POI ID，`text:` 保留自由文本；未知或裸 UUID 引用 fail closed。
- 运行时门禁：只有 VERIFIED 才产生 v9 completion 并创建正式版本；UNVERIFIED/NEEDS_REPAIR 产生 review-required v1，进入 WAITING_USER 候选预览。
- v8/v2 schema 冻结不改；v8 completion 在 Java runtime fail closed（不创建版本）。

## B6W：最新任务发现端点与前端统一 outcome 门禁

- **REST**：新增只读 `GET /api/trips/{tripId}/planning-tasks/latest`，返回 owner 的 trip 最新 `PlanningTaskResponse`（`ORDER BY created_at DESC, id DESC LIMIT 1`）；无任务、trip 不存在或非 owner 统一 404；复用 `terminalMetadata`/`PlanningTaskOutcomeReadModel` 的 fail-closed 语义；纯读、不产生 task event、不改 DB schema。
- **前端统一 outcome parser**：`apps/web/src/lib/feasibility.ts` 提供 `readPlanningTaskOutcome`（Task API）与 `readPlanningEventOutcome`（SSE live/replay），两者共享同一真值表：SUCCEEDED/PLANNING_COMPLETED 仅接受 VERIFIED report + 合法 evaluation（candidate 必须缺失）；WAITING_USER/PLANNING_REVIEW_REQUIRED 仅接受 NEEDS_REPAIR/UNVERIFIED report + 合法 candidate（evaluation 必须缺失）；QUEUED/RUNNING/FAILED/CANCELLED 不得携带任何 outcome 字段；status 与 eventType 不匹配或任一字段 malformed 一律判定 malformed。
- **malformed 前端行为**：terminal 状态 + "规划结果无法安全读取，请重新规划"；清空 report/candidate/evaluation；不刷新正式 itinerary；不显示任何权威状态标签。
- 前端对可行性报告的运行时读取（`readFeasibilityReport`）执行与 Java `FeasibilityReportValidator` 一致的门禁：schemaVersion 必须为整数 1；validatorVersion 白名单（feasibility-v1、hard-validator-v1..v5）；必填数组缺失即拒绝；summary 为非负整数；RepairAttempt 最多三条且序号连续，动作/触发规则非空、日期/实体/指纹有界并严格校验；typed ref 空值或非规范 UUID 归为 unknown。

## B7：有界修复与进度 v2

- Python 在首轮报告为可修复 `NEEDS_REPAIR` 时进入最多三轮 repair/replan；每轮后完整重验 11/11，只有最终 `VERIFIED` 才产生 completion v9。
- `planning-progress-event-v2` 新增 `REPAIRING`；statistics 必须包含 1..3 的 `attemptIndex` 与 1..16 的 `actionCount`。Java 持久化同一任务的多条递增序号事件，Web 对 live/replay 使用同一严格 reader。
- `hard-validator-v5` 的 RepairAttempt 记录触发规则、动作、受影响日期/实体、前后指纹和结果状态；Python、Java、Web 均执行三次上限和连续序号门禁。
- 无进展、重复失败、证据未知、无合法动作、Provider 失败或三轮耗尽不会伪造成功；仍通过 review-required v1 或既有失败事件收口。

## B8：candidate-validation v1

- `PLANNING_CANDIDATE_VALIDATION_REQUESTED` / `planning.candidate-validation` 同时承载 EDIT 与 ROLLBACK；`candidateType` 必须与 `taskType` 匹配。
- payload 必填 baseline trip/itinerary、idempotencyKey、changedDates、impactedDates、完整 candidate、knowledge 和 planningContext；ROLLBACK 额外必填 `rollbackFromVersionId`。
- `impactedDates` 必须严格等于 changedDates 在旅程内扩展出的 N-1/N/N+1；Python 模型和 Java producer 双端校验。
- candidate activity/transit 的 `locked` 为 v9/review 向后兼容可空字段；candidate command 必须显式保存实际锁状态。
- 共享 fixtures 位于 `contracts/fixtures/planning-candidate-validation-command-v1/`，包含 EDIT、ROLLBACK 正例与 identity 反例。

## B10：结构化日志字段契约

跨服务日志字段语义对齐（Java camelCase / Python snake_case）：`traceId`/`trace_id`、`eventId`/`event_id`、`taskId`/`task_id`、`tripId`/`trip_id`、`runId`/`run_id`、`taskType`/`task_type`、`candidateType`/`candidate_type`、`schemaVersion`/`schema_version`、`eventType`/`event_type`、`outcomeStatus`/`outcome_status`、`attemptIndex`/`attempt_index`、`provider`、`operation`、`retryable`、`fallbackAttempted`/`fallbackSucceeded`、`retryCount`。禁止记录完整 payload、原始 Provider 响应、secret、完整 evidence/raw statement 与用户自由文本全文；见 [可观测性](../operations/可观测性.md)。
