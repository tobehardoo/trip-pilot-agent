面向第一次进入仓库的开发者或 Agent：如何独立定位 TripPilot 主链、修改常见功能、理解不变量。本文档只给结构与指针，不复制源码；代码永远是最终事实。

## 1. 仓库目录与职责

```text
apps/web               Vue 3 前端（旅行工作台、SSE 进度、版本面板、可行性面板）
apps/travel-server     Spring Boot 3.5 业务服务（领域 API、任务、SSE、Outbox、持久化）
apps/agent-service     Python 规划 Agent（Provider、硬校验、repair、消息消费）
contracts              消息契约 JSON Schema 与共享 fixtures
infra/docker           数据库扩展镜像（postgis + pgvector）
scripts                链接检查、smoke、golden HTTP 场景等仓库脚本
docs                   index.md 为入口；architecture / development / operations / product
```

三端边界一句话：**Python 只算行程与硬校验结论；Java 只持久化并转发给 Web；Web 只展示权威结论。**

## 2. 创建规划完整调用链

```
REST POST /api/trips/{id}/planning-tasks
→ PlanningTaskService.create（冻结约束快照 + guide facts，插 planning_task）
→ Outbox（PLANNING_CREATE_REQUESTED v3, routing key planning.create）
→ RabbitMQ → Python handle_delivery（worker/amqp.py）
→ process_planning_create（worker/processor.py）
   → provider.plan（infrastructure/amap 或 demo/planning_provider.py）
      → daily_schedule.py（DayPlan）→ trip_skeleton.py（TripSkeleton）
      → validation_projection.py（ValidationInputs）
   → run_validation（feasibility/validator.py，11 规则）
   → _repair_if_needed（feasibility/repair，最多三轮）
   → VERIFIED → PlanningCompletedEventV9 + evaluation
     | 其余 → PlanningReviewRequiredEvent v1
→ RabbitMQ → PlanningCompleted/ReviewRequiredEventListener + Parser（fail-closed）
→ PlanningCompletionService（事务：建不可变版本 + feasibility report + 任务 SUCCEEDED）
  或 PlanningReviewService（WAITING_USER + 候选，不建版本）
→ PlanningTaskEventCreated → SSE（PlanningTaskEventStreamService）
→ Web TripWorkspace.vue：attachPlanningStream → applyOutcomeState → 权威面板
```

## 3. edit / rollback 调用链

```
编辑：POST /itinerary/edits、/edits/commit → ItineraryService.validateEditCandidate(s)
回滚：POST /itinerary/rollbacks → ItineraryVersionService.validateRollback
两者都：冻结 immutable candidate + N-1/N/N+1 impacted dates
→ PlanningTaskService.createCandidateValidation（EDIT_VALIDATE/ROLLBACK_VALIDATE）
→ outbox → Python process_candidate_validation → CandidateValidationProvider（刷新路由 + 重投影）
→ 同一 Hard Validation + bounded repair
→ VERIFIED → completion v9 → createCandidateVersion → USER_EDIT/ROLLBACK 版本 + 切 current
| 其余 → review v1 → WAITING_USER，current 不变
```

关键不变量：**candidate 永远不直接写正式版本；历史版本内容被复制时从不复制历史 feasibility report。**

## 4. Feasibility / repair 调用链

```
ValidationContext（command + itinerary + budget + TripSkeleton + ValidationInputs + validation_time）
→ _RULE_DISPATCH 按 catalog 顺序执行 11 个 assess_*（feasibility/rules/）
→ RuleResult（PASS/FAIL/UNKNOWN/NOT_APPLICABLE + reasonCode）
→ build_feasibility_report 聚合：FAIL→NEEDS_REPAIR；UNKNOWN/缺规则→UNVERIFIED；否则 VERIFIED
→ compute_itinerary_fingerprint（三端同算法：排序 key、exclude_none=False、SHA-256）
→ repair：session.py 限三轮 → engine.py 选择动作 → 每轮后完整重验
```

## 5. Provider / fallback 调用链

- `provider_modes`（DEMO_ONLY / REAL_ONLY / REAL_WITH_EXPLICIT_FALLBACK）见 `providers/errors.py` 与 `worker/amqp.py::build_planning_provider`。本地默认 **DEMO_ONLY**（`compose.prod.yaml` 与 `WorkerSettings` 双缺省一致；显式 REAL_ONLY 且空 AMap key 会在 Worker 启动期 fail-fast）。认证/权限类 Provider 错误永不回退。
- 重试：`providers/retry.py`（次数/退避/抖动/总时长）；回退：`workflow/planner_pipeline.py::FallbackPlanningProvider`（白名单类别，来源追踪）。
- 安全边界：Demo 不伪造 opening evidence、不伪造 confirmed 住宿、meal 投影显式 UNAVAILABLE；AMap provider evidence 永不升级为 hard-constraint eligible。

## 7. PostgreSQL 主要表与 Flyway

- `business.planning_task`（六态：QUEUED/RUNNING/SUCCEEDED/WAITING_USER/FAILED/CANCELLED + baseline + traceId）
- `business.planning_task_event`（PLANNING_QUEUED/PROGRESS/COMPLETED/REVIEW_REQUIRED/FAILED/CANCELLED，SSE 数据源）
- `business.outbox_event`（PENDING/SENT/RESCHEDULED/DEAD）
- `business.itinerary_version`（不可变版本 + current 标记 + version_source）
- `business.itinerary_feasibility_report`（V33 JSONB 无损 report）
- V34 增 candidate 校验列与 CHECK 约束；Flyway 顺序迁移 V1→V34，禁止原地改已发布 migration。

## 8. Task API / SSE / Web 状态机

- Task API 六态真值表：`PlanningTaskOutcomeReadModel`（SUCCEEDED 仅接受 VERIFIED report + evaluation 且无 candidate；WAITING_USER 仅接受 UNVERIFIED/NEEDS_REPAIR + candidate 且无 evaluation；其余状态不得携带 outcome 字段；任何不匹配 → malformed fail-closed）。
- Web 单一入口：`apps/web/src/lib/feasibility.ts` 的 `readPlanningTaskOutcome` / `readPlanningEventOutcome` 共享同一真值表；`TripWorkspace.vue::applyOutcomeState` 是唯一状态应用点。
- SSE 重连：Last-Event-ID + 终端事件只应用一次；Web 侧另有单 stream 内的 terminal 短路（首个终态帧后忽略后续帧）。

## 13. 不变量与禁止事项

1. VERIFIED 才能创建正式版本；NEEDS_REPAIR/UNVERIFIED 只能形成 review candidate。
2. UNKNOWN/STALE/CONFLICTING evidence 不得形成 hard PASS；hard_constraint_eligible 仅限 VERIFIED。
3. AREA_ESTIMATED/UNRESOLVED 住宿不得形成 continuity PASS；Demo 不伪造证据。
4. repair 最多三轮，历史完整；evaluation 只在 VERIFIED 后执行。
5. stale baseline 不覆盖 current；duplicate 事件幂等；fingerprint 不匹配 fail-closed。
6. 版本创建只允许经 PlanningCompletionService 事务；禁止 bypass parser 直连 service 制造版本。
7. 禁止记录完整 payload、secret、Provider 原始响应；MDC 必须在 finally 恢复。
8. 禁止原地修改已发布 Flyway migration 与已发布 schema；契约演进必须新增版本。
9. 禁止把环境失败当业务失败、禁止用 skip/弱化断言制造通过。
10. WAITING_USER 只能被用户显式“放弃候选”转为 CANCELLED：这是 Java 本地转换（不发 cancel command、不建版本/报告、不动 current）；候选永不接受为正式版本。终态（含 WAITING_USER）后的迟到 progress 被幂等忽略，不入 DLQ。

## 14. 调试断点建议

- Python：`process_planning_create` 入口；`run_validation` 返回后看 report.status；`_repair_if_needed` 每次循环边界。
- Java：三个 listener 的 parser.parse 后；`PlanningCompletionService.handleInScope` 各分支；`PlanningReviewService.validateCandidateIntegrity`。
- Web：`TripWorkspace.vue::applyOutcomeState`（所有 outcome 的唯一落点）；`lib/feasibility.ts` reader 返回 malformed 处。
- 跨层关联：日志 traceId/taskId/tripId（Java MDC camelCase、Python snake_case）在两端日志与事件 headers 中一致。
