## 1. 文档用途与权威边界

本文档用于让新的 Agent 在没有聊天历史的情况下，能够安全地恢复上下文、选择下一个批次、持续执行、生成证据并交给另一个 Agent 验收。

本文档是“未来实施顺序、完成标准与验收纪律”的权威来源；产品定位以产品概述为准，当前能力摘要以项目路线图为准，具体代码与测试始终是最终事实来源。文档与代码不一致时，Agent 必须先报告差异，不得为了让文档看起来正确而伪造完成状态。

本文档不授权 Agent 自动执行以下操作：

- push、创建或修改 PR；
- force push、rebase、reset、clean、stash 或覆盖用户改动；
- 读取、输出或提交私有 `.env` 与真实密钥；
- 部署到公网服务器；
- 将 staging、TLS、registry digest、固定出口 IP、24 小时 soak 重新设为项目完成门禁。

## 2. 产品完成目标

系统的最终目标不是“生成一份看起来合理的行程”，而是在本地环境形成以下闭环：

1. 规划器生成候选行程和完整验证输入。
2. 独立 Hard Validator 对全部必需规则给出 PASS、FAIL、UNKNOWN 或 NOT_APPLICABLE。
3. Feasibility Report 聚合为 VERIFIED、NEEDS_REPAIR 或 UNVERIFIED，并成为唯一硬可行性结论。
4. 只有 VERIFIED 候选才能成为当前正式行程版本。
5. NEEDS_REPAIR 或 UNVERIFIED 候选进入 WAITING_USER，完整保留候选、证据和失败原因，但不修改当前正式版本。
6. 可修复失败进入有界 repair/replan，每轮修复后重新验证。
7. 用户编辑和回滚均生成新的不可变候选并重新验证，不继承历史验证状态。
8. 前端准确区分可行性与体验评分，展示证据、受影响节点、修复过程和剩余问题。
9. DEMO_ONLY 可完成本地主旅程；缺少真实 Provider 证据时可以生成候选，但必须是 UNVERIFIED，不能伪造 VERIFIED。

## 3. 不可变领域语义

### 3.1 报告与规则状态

Feasibility Report 只允许：

- `VERIFIED`：全部必需规则已执行，没有 FAIL 或 UNKNOWN，且没有缺失规则；
- `NEEDS_REPAIR`：至少一条规则为 FAIL；
- `UNVERIFIED`：没有 FAIL，但至少一条 UNKNOWN，或仍缺少必需规则。

Rule Result 只允许：

- `PASS`；
- `FAIL`；
- `UNKNOWN`；
- `NOT_APPLICABLE`。

聚合顺序固定为：FAIL 优先于 UNKNOWN，UNKNOWN 优先于缺失规则，只有全 PASS/NOT_APPLICABLE 且无缺失规则时才是 VERIFIED。

### 3.2 正式版本门禁

- `PLANNING_COMPLETED` 活跃运行时契约只能是 schema v9。
- v9 必须同时携带 VERIFIED Feasibility Report 和 PlanEvaluation。
- 只有 v9 VERIFIED completion 才能原子创建正式 itinerary version、保存报告并更新 current version。
- completion v1–v8 仅保留历史契约价值，运行时必须 fail closed。
- `PLANNING_REVIEW_REQUIRED` v1 只允许 UNVERIFIED 或 NEEDS_REPAIR，不允许 evaluation，不创建正式版本。
- 没有报告、报告无法解析、指纹不匹配或报告语义不一致时一律 fail closed。

### 3.3 证据安全

- UNKNOWN、STALE、CONFLICTING 或 `hard_constraint_eligible=false` 的营业时间证据不得产生硬 PASS/FAIL。
- 营业时间硬 PASS/FAIL 必须至少有一条 VERIFIED 且 eligible 的依据。
- Provider、category、fallback 或 Demo 默认值不得被升级为官方事实。
- Feasibility Report 与候选 itinerary 必须通过指纹绑定；跨语言序列化必须使用同一字段、null、排序和 UTF-8 规则。
- task event、DB 和 API 中的 activity/transit 引用必须能够映射到实际节点，不得保留无法定位的临时 ID。

### 3.4 编辑、回滚与修复

- 自动 repair 最多三轮；只能修改报告标记为 repairable 的问题和明确受影响范围。
- 每轮必须记录触发规则、动作、日期、实体、前后指纹和结果状态。
- 编辑后的候选先是 UNVERIFIED，不得立即替换 current version。
- 编辑验证范围至少覆盖 N-1、N、N+1，并包含跨日住宿边界。
- 回滚只复用历史内容，不复用历史验证结论；必须用当前约束与当前证据重新验证。
- 任何修复、编辑或回滚只有在重新得到 VERIFIED 后才能提升为正式 current version。

## 5. Agent 长任务执行协议

### 5.1 角色分离

一个完整批次由三个角色组成：

1. **规划 Agent**：核对代码事实，定义批次范围、语义、RED 用例、门禁和非目标。
2. **执行 Agent**：严格 TDD 实现，保留 RED→GREEN 证据，完成后保持 unstaged 并停止。
3. **验收 Agent**：只读审计业务实现、测试和范围，主动寻找假绿、跨层断链、错误 fixture 和未被测试覆盖的绕过路径；唯一允许的写入是对应批次的 `acceptance-report.md`。

执行 Agent 不得给自己的批次作最终 PASS。只有验收 Agent 返回 PASS 后，才允许单独执行 Git 提交收口。

从本文生效后，批次计划与报告统一保存在：

```text
docs/execution/<batch-id>/plan.md
docs/execution/<batch-id>/execution-report.md
docs/execution/<batch-id>/acceptance-report.md
```

规划 Agent 在执行开始前创建 `plan.md`，其中列出精确目标、允许路径、禁止路径、RED 用例和门禁。执行与验收 Agent 分别写对应报告；聊天输出可以更简短，但不得成为唯一证据。当前已经开始的 B6 是例外，其恢复断点保存在本文第 4.2 节，B6J.1 执行开始时补建上述三个文件。

### 5.2 状态机

每个批次只能按以下状态迁移：

```text
NOT_STARTED
  → PLANNED
  → IN_PROGRESS
  → READY_FOR_REVIEW
  → NEEDS_FIX → IN_PROGRESS → READY_FOR_REVIEW
  → ACCEPTED_PENDING_COMMIT
  → COMMITTED
```

外部条件确实缺失时可以进入 BLOCKED；恢复后回到 IN_PROGRESS。`PASS` 是验收结论，对应状态 `ACCEPTED_PENDING_COMMIT`；只有 Git 提交成功后才是 COMMITTED。

验收结论到状态的映射固定为：

| 验收结论 | 批次状态 |
| --- | --- |
| `PASS` | `ACCEPTED_PENDING_COMMIT` |
| `NEEDS_SMALL_FIX` | `NEEDS_FIX` |
| `NEEDS_CORRECTION` | `NEEDS_FIX` |
| `BLOCKED` | `BLOCKED` |

验收 Agent 只写 acceptance report，不修改本文进度表。PASS 后由独立 Git 收口任务把本文状态直接更新为 COMMITTED，并与实现、测试和三份批次报告一起显式暂存；提交失败时不产生持久化错误状态。

### 5.3 单批次循环

每个批次必须遵循：

1. 前置安全检查；
2. characterization tests，锁定既有正确行为；
3. RED：新增测试必须因真实缺陷失败；
4. GREEN：最小实现关闭 RED；
5. REFACTOR：去除重复，不扩大语义；
6. 定向测试；
7. 受影响层回归；
8. 全量门禁；
9. `git diff --check` 和范围审计；
10. 输出 `READY_FOR_REVIEW` 并停止；
11. 独立验收；
12. 验收 PASS 后进入临时状态 `ACCEPTED_PENDING_COMMIT`，只记录在 acceptance report；
13. 单独执行 Git 收口：把本文对应状态直接改为 `COMMITTED`，将实现、测试、批次三份报告和本文一起显式暂存并提交；
14. 提交成功即视为 `COMMITTED`，commit hash 写入 Git 收口报告，不 amend 刚创建的提交；下一次更新本文时再补充 hash，不为补 hash 单独制造提交。

同一执行 Agent 可以在一个批次内部持续工作直到门禁完成；不得未经验收跨入下一个批次。

### 5.4 中断恢复

长任务被中断或上下文压缩后，Agent 必须：

1. 读取本文档；
2. 从 `docs/execution/<batch-id>/` 读取最近的 plan、execution-report 和 acceptance-report；当前 B6 首次恢复时读取第 4.2 节；
3. 检查 Git 状态和 staged 集；
4. 复跑最近一个已完成 RED/GREEN 小组的定向测试；
5. 从第一个未完成验收项继续，不得重写已完成模块；
6. 如果发现文件已经部分实现，先补 characterization test，禁止假设其正确或直接覆盖。

### 5.5 强制 Git 安全规则

- 默认保持 unstaged；只在明确的 Git 收口任务中 stage/commit。
- 只能使用显式路径 `git add -- <approved paths>`，禁止 `git add .`、`git add -A`、`commit -a`。
- 禁止 amend 先前已验收提交，除非用户明确要求。
- `.omo/`、`.serena/`、`docs/audits/` 和私有 `.env` 永远不纳入业务提交。
- 不得删除未跟踪目录来获得“干净工作树”。
- 未经用户明确授权，不 push、不创建 PR。
- 一批一验收一提交；不把多个尚未验收批次长期堆在同一个工作区，也不在最终总验收时 squash 已验收提交。

## B7A — 有界 Repair Engine

### 目标

建立纯函数、确定性、最多三轮的 repair engine，不依赖 Worker、网络、数据库或当前时间。

### 必做范围

1. 建立 RepairAction catalog，明确每类 action 可处理的 reasonCode。
2. 只处理 `repairable=true` 的 FAIL。
3. 动作范围限制在 affected dates/entities；跨日问题允许扩展到 N-1/N/N+1。
4. 每轮生成不可变新候选，不原地修改输入。
5. 每轮重新运行完整 Hard Validator 11/11。
6. 记录最多三条 RepairAttempt。
7. 指纹未变化、同一失败重复、成本/日期越界或无合法动作时立即停止。
8. FAIL 不得通过删除 finding、降级 evidence 或改写报告聚合器来“修复”。

执行预算固定为：最多三轮；每轮最多一次 planner/replan 调用；默认最多覆盖三个日期（N-1/N/N+1）。底层 Provider 只使用现有 Provider timeout/retry 配置，repair engine 不得在其外再包一层无限重试。只有报告明确影响全旅程时，规划 Agent 才能为该用例批准扩大日期范围。

### 首批动作

- 调整活动开始/结束时间以满足 opening/last-entry；
- 在 duration min/max 内缩放；
- 移除或替换重复普通 POI；
- 补齐可计算的 transit leg；
- 调整显式 meal placement；
- 不自动替换 must-visit，不伪造住宿或官方证据。

### 验收门禁

- 每个 action RED→GREEN；
- 确定性、输入不可变、循环检测和三轮上限测试；
- FAIL>UNKNOWN 聚合不变；
- 失败历史完整、顺序稳定、有界；
- Python feasibility coverage 不低于 80%，全量测试通过。

### 完成标志

`B7A_READY_FOR_REVIEW`，保持 unstaged。

## B7B — Repair/Replan 运行时接入

### 目标

在 worker 中对可修复失败执行有界 repair，对需要 Provider 的部分发起有界局部 replan，并在每轮后重新验证。

### 必做范围

1. VERIFIED 首轮直接 completion，不做 repair。
2. NEEDS_REPAIR 且存在支持的动作时进入 repair。
3. 修复成功 VERIFIED → completion v9。
4. 三轮后仍失败或无法修复 → review v1，保留全部 attempts。
5. UNVERIFIED 不得通过猜测证据变成 VERIFIED。
6. 使用 B7A 固定预算：最多三轮、每轮一次 planner/replan 调用、默认最多三个日期；底层调用只使用既有 Provider timeout/retry，不叠加第二套重试。
7. 进度事件展示 attempt index 和阶段，但不泄露原始 Provider 响应或 secret。

### 验收门禁

- worker flow 测试覆盖 0/1/3 次修复、无进展和 Provider 失败；
- completion/review report 指纹匹配最终候选；
- Java 能无损解析非空 repairAttempts；
- Web 能显示修复历史；
- 全层门禁通过。

### 完成标志

`B7B_READY_FOR_REVIEW`，保持 unstaged。

## B8A — 编辑后重新验证

### 目标

用户编辑不再直接产生未经验证的 current version。

### 必做范围

1. 候选持久化模型已经确定：复用 B6 的 `planning_task_event` JSONB/read model 保存不可变 candidate，不向 `itinerary_version` 写入未验证版本，不新增第二套 candidate 表。
2. 新增统一 `PLANNING_CANDIDATE_VALIDATION_REQUESTED` v1 command；payload 使用 `candidateType=EDIT` 或 `ROLLBACK`，携带 candidate itinerary、impactedDates、当前约束和 baseline。
3. preview edit 执行快速 provisional validation；apply edit 创建 UNVERIFIED 不可变 candidate，并创建 taskType=`EDIT_VALIDATE` 的 planning task/outbox command。
4. 自动计算 impacted dates，并扩展为 N-1/N/N+1。
5. 对受影响交通、住宿边界和证据重新构建 ValidationInputs。
6. Worker 消费 candidate-validation command，仍只产生现有两类 outcome：VERIFIED 使用 completion v9，NEEDS_REPAIR/UNVERIFIED 使用 review-required v1。
7. 完整重新验证后：
   - VERIFIED：通过同一个 v9 completion 正式版本门禁原子提升为 current；
   - NEEDS_REPAIR/UNVERIFIED：通过 review-required 保持 candidate，current 不变。
8. 编辑过程中不得继承父版本报告。

candidate 的查询生命周期固定为 task-scoped：通过 planning task ID 查询 Task API 与 SSE；不新增 trip 级“latest candidate”隐式查询。

B8A 只实现 edit candidate 所需的 ValidationInputs/TripSkeleton adapter；B9 不重写它，而是补齐 Demo/replan 等其他生产路径并加入主动放置优化。

- currentVersion 在未 VERIFIED 前不变化；
- 受影响范围不少算、不无限扩大；

`B8A_READY_FOR_REVIEW`，保持 unstaged。

## 8. 验收 Agent 检查方法

验收 Agent 不应只复述执行报告。至少完成：

1. 对照 `docs/execution/<batch-id>/plan.md` 的允许路径和执行报告精确文件清单检查 `git diff --name-status`；
2. 阅读生产代码而不是只读测试；
3. 从真实入口追踪一条成功和一条失败链；
4. 检查 producer routing/serialization 与 consumer binding/parser 是否一致；
5. 检查 fixture 是否由真实模型生成，是否因空数组避开复杂结构；
6. 尝试绕过 parser 直接调用 service；
7. 检查事务中写入顺序和回滚；
8. 检查历史/兼容路径是否能绕过新门禁；
9. 检查 UNKNOWN/STALE/CONFLICTING 是否被错误升级；
10. 检查 API/Web 是否重新推导权威状态；
11. 复跑与风险成比例的定向和全量门禁；
12. 输出具体文件、行号、复现输入和影响。

验收结论只允许：

- `PASS`：全部批准目标完成，无阻塞问题；
- `NEEDS_SMALL_FIX`：范围内有明确、有限的小修；
- `NEEDS_CORRECTION`：存在运行时断链、门禁绕过、事务或契约问题；
- `BLOCKED`：缺少必要外部条件且已穷尽安全替代方案。
