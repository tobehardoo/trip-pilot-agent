## 目标与边界

本次重构的目标是让用例编排、领域规则和基础设施适配器的职责更清楚，同时保持既有
REST 语义、数据库迁移历史和消息兼容性。重构期间同时交付了行程编辑与局部重规划，
因此原报告中“不新增功能、不修改 API、不修改 MQ Schema”的表述已经失效。

不变的架构原则：

- Java 拥有用户、旅行、规划任务、攻略与行程版本等业务事实。
- Python 拥有候选生成、Provider 调用、知识检索和约束求解。
- 跨服务只通过版本化消息契约通信。
- 行程版本不可变；任何编辑或局部重规划都创建新版本。
- 外部 Provider 必须有超时、错误分类、缓存和明确降级。

## 已完成

### Java

- 基础设施代码归入 `infrastructure`，消息监听、Outbox、持久化适配器边界更清楚。
- 新增应用与领域包，为后续用例提取提供稳定命名空间。
- 规划完成后的版本写入集中到 `ItineraryService`/`ItineraryVersionPersister` 协作路径。
- 行程编辑支持预览、删除、移动、锁定和交通方式调整。
- 局部重规划使用独立 `REPLAN` 命令、基线版本和受影响日期。

### Python

- Worker 入口、应用编排、规划模型、Provider 与基础设施职责已分层。
- CREATE 与 REPLAN 使用独立应用服务。
- 高德规划 Provider、知识检索和消息传输从原始处理器中拆出。
- 共享时区与文本匹配规则已集中，重复实现减少。

### Web

- API、路线、地图、交通估算和弹窗行为提取为独立模块。
- 行程详情支持编辑预览与局部重规划。
- 测试覆盖 API、路由、地图、交通方式、攻略和核心页面行为。

## 后续重构顺序

1. 先用行为测试锁定行程编辑、局部重规划和规划完成落库。
2. 提取纯规则或只读查询，不改变事务边界。
3. 提取写入用例，每次只迁移一条写路径。
4. 增加架构边界测试，禁止应用层依赖 Web 或具体 MQ 实现。
5. 每一步运行 Java、Python、Web 全量门禁；不要在同一提交中混入新产品功能。

## 完成定义

架构重构不是以目录数量或文件行数单独判定。只有同时满足以下条件才算完成：

- 业务行为和消息兼容性测试无退化；
- 写入路径与事务所有者唯一；
- 领域/应用层不依赖控制器、MQ 客户端或具体数据库驱动；
- 大文件的职责可由名称直接说明，且修改一种行为不需要触碰无关层；
- 独立代码审查无 Critical 或 Important 问题。
