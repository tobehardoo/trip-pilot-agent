# 规划算法与 Agent 工作流

## 为什么分三步走：候选过滤 → 偏好排序 → 约束求解

旅行规划的难点不是「推荐景点」，而是保证时间、交通、预算和用户约束同时成立。

如果一步到位让 LLM 直接生成行程，会出现三个问题：
1. LLM 不了解实时路线距离和通勤时间
2. LLM 可能推荐不存在或已关闭的地点
3. LLM 无法保证必去地点全部安排、硬预算不突破

因此 TripPilot 采用三段式 Pipeline：

```
用户需求（结构化约束）
  → Step 1: 候选 POI 召回（高德 + RAG + 攻略事实）
  → Step 2: 过滤去重 + 偏好排序（确定性规则，不依赖 LLM）
  → Step 3: 约束求解（OR-Tools CP-SAT，硬约束建模）
  → 不可变行程版本
```

**Step 1 负责广度**：从高德搜索同城 POI，从知识库检索相关区域和主题，从攻略中提取用户标记的事实。此阶段不追求精确，追求不遗漏关键候选。

**Step 2 负责筛选**：按名称相似度去重（`text_matches`），排除用户明确不去的类别，按偏好、必去标记、攻略影响打分排序。此阶段是可测试、可审计的确定性逻辑。

**Step 3 负责可行性**：将排名靠前的候选输入 OR-Tools，在时间窗、交通、预算和固定安排的硬约束下求解。不可行时返回冲突原因而非虚假行程。

V1.3 在进入 Step 1 前增加一个固定输入边界：Java 已经完成 TTL 检查、来源复核与冲突
合并，并把结果冻结为 `PlanningContextSnapshot`。Worker 不在 Pipeline 中调用情报
Provider 或抓取网页。

## 为什么用 OR-Tools CP-SAT 而不是启发式

多日旅行规划接近 **Prize-Collecting VRP with Time Windows**：

- 每一天对应一辆虚拟车辆
- 酒店是每天起点和终点（首尾两天例外，用到达/返程地点）
- 景点有时间窗、服务时长、费用和偏好收益
- 必去节点不可跳过，可选节点有跳过惩罚
- 目标：在满足硬约束的前提下，最大化偏好收益、最小化通勤和软约束违反

CP-SAT 求解器擅长处理这类离散组合优化问题：
- 原生支持时间窗和累积约束
- 可以设置求解时间上限，超时返回当前最佳可行解
- 无可行解时可以通过松弛分析定位冲突

约束模型的设计原则：
- **硬约束**（必须满足）：必去地点、到返时间、预约时间、预算硬上限、锁定活动
- **软约束**（尽量满足）：偏好匹配、减少步行、节奏均衡、预算期望附近
- **上下文约束**（条件满足）：天气、季节、同行类型、行动能力

软约束违反产生惩罚成本，不导致无解。硬约束违反必须向用户解释冲突，不静默放宽。

## 可信事实如何影响规划

事实先按适用日期和景点身份匹配，再执行类别规则：

| 事实 | 新鲜、审核官方来源 | Provider/社区或 stale |
|---|---|---|
| 临时关闭 | 排除对应日期景点 | 不排除，只提示并降低置信度 |
| 预约要求 | 形成约束或高优先级提示 | 仅提示 |
| 开放时间 | 进入对应日期时间窗 | stale 时仅提示，不静默形成硬窗口 |
| 官方门票 | 进入预算估算 | 高德参考消费单列，不覆盖官网门票 |
| 天气 | 只影响 `effectiveDate` 当天的室内/室外分数 | stale 时降低权重并提示 |
| 社区攻略 | 不形成硬约束 | 只影响排序、提示和解释 |

冲突不能静默丢弃。快照同时保留采用事实、被降级事实、采用原因和是否需要人工复核。
每个实际改变排除、时间窗、预算或排序的事实生成 `PlanningFactImpact`，包含事实 ID、
日期、效果、目标 POI、原因、来源和核验时间。解释来自规则、评分变化与求解约束，不要求
模型解释确定性求解过程。

## Provider 设计

### 为什么需要 Provider 抽象

系统依赖多个外部数据源：高德 POI、高德路线、天气、城市知识库、LLM。如果不加抽象，规划代码会直接包含 HTTP 调用、缓存逻辑和错误处理——任何 Provider 变更都要求修改规划核心。

Provider 协议定义了统一接口：

```python
class MapProvider(Protocol):
    async def search_pois(self, request: PoiSearchRequest) -> ProviderResult[list[Poi]]: ...

class RouteProvider(Protocol):
    async def get_route(self, request: RouteRequest) -> ProviderResult[RoutePlan]: ...
```

每个 Provider 实现管理自己的：
- **超时和重试**：瞬时错误指数退避，认证错误直接失败
- **错误分类**：参数错误、限流、额度耗尽、Schema 变化
- **缓存策略**：POI 秒级 TTL、路线小时级 TTL
- **降级路径**：真实模式失败时回退到 Demo Provider（带明确标记）

### 为什么有 Demo Provider

Demo Provider 不是「测试桩」，而是系统的正式运行模式之一：

- 离线或无 Key 环境下的可复现演示
- 自动化测试不消耗 API 额度
- 固定评测输入保证结果可比较
- 前端开发无需等待后端 API Key 配置

Demo 模式的结果始终标记 `provider=DEMO`，前端和水印明确展示「演示模式」，不把 Demo 数据伪装成实时结果。

## 约束求解的「无解处理」

OR-Tools 返回无解时，系统不会立即向用户报错，而是按顺序尝试：

1. 检查必去地点间是否有时间冲突（两个必去地点预约时间重叠）
2. 检查返程时间和最后一个活动是否有冲突
3. 移除最低偏好的可选活动后重新求解
4. 尝试将步行段降级为出租车（标记费用为估算）
5. 放宽可自动放宽的软约束（如容忍稍长的步行）
6. 仍无解 → 暂停，向用户呈现冲突分析，等待用户选择

每次放宽必须记录原因。硬约束不得静默放宽。

## 局部重规划

### 为什么不全量重规划

用户编辑行程（删除一个活动、移动一个活动、锁定一个活动）后，如果重新执行完整的规划 Pipeline，会出现两个问题：

1. **体验差**。全量重规划耗时 10-30 秒，而且可能改变用户已确认的其他日期安排。用户只是想删除第三天的某个活动，结果第一天和第四天也被重新安排了。
2. **浪费资源**。高德 API 调用有 QPS 和日额度限制。全量重规划意味着重新查询所有天的 POI 和路线，而用户实际上只修改了其中一天。

### 影响范围规则

局部重规划的核心问题是「哪些天需要重建」。规则是：

- **删除普通景点** → 只重规划当天。删除一个活动只是为当天腾出了一个时段，不影响其他天。
- **修改当天结束时间** → 重规划当天及与相邻天的交通段。结束时间改变可能影响跨天衔接。
- **降低总预算** → 需要全局重排。预算约束是跨天的——某天省下的预算可能影响其他天的可选活动。
- **修改酒店位置** → 重新计算所有天的首尾路线。酒店是每天的起点和终点，改变它对每一段通勤都有级联影响。
- **锁定活动** → 只调整该活动所在天的周边内容。锁定意味着「这个地点和时段不能变」，其余照旧。

这些规则的依据是：**只重建受影响的约束边界，不触动无关的已确认内容**。

重规划输入必须包含：当前版本 ID（防止并发冲突）、完整基线行程（含锁定状态）和允许
修改的日期范围。结果创建为独立版本，不影响未修改的日期。版本差异与回滚的用户界面
属于后续 `TP-REQ-005`，当前只能依靠不可变版本数据保留恢复基础。

## 任务取消

### 为什么不能用强制杀进程

如果用户在规划进行到一半时点击取消，最粗暴的做法是直接杀 Python Worker 进程。但这会引入新问题：

- Worker 可能已经向数据库插入了部分行程数据（例如已保存了两个天的活动），杀进程意味着数据库中有不完整的行程
- RabbitMQ 消息未 ack，Worker 重启后会重新消费——同一任务被执行两次
- 已发出的高德 API 请求无法撤回（HTTP 请求已离开服务器），但我们可以停止后续步骤

因此取消设计为**协作式**而非强制式：

1. Java 将任务状态更新为 `CANCELLING` 并通过 RabbitMQ 发布取消命令
2. Python Worker 在每个关键步骤开始前检查进程内取消注册表——如果已标记取消，不再进入后续计算
3. 已发出的 HTTP 请求设置超时上限（例如 10 秒），在超时内等待响应后不再发出新请求
4. Worker 在取消路径中执行最小清理：发布取消完成事件、正常 ack 消息
5. Java 收到取消确认后将状态更新为 `CANCELLED`

这个设计的代价是取消有延迟——如果 Worker 正在执行 OR-Tools 求解，它需要等当前求解完成（有超时上限）后才能在下一个检查点响应取消。对于 V1 的规划周期（10-30 秒），几秒的延迟是可以接受的。
