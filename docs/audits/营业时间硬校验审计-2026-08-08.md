## 1. Executive Summary

当前系统**已经存在营业时间事实管道**，但**尚未形成可供硬校验消费的结构化营业时间语义**：

- Guide Intelligence 已能从攻略抽取 `OPENING_HOURS` 事实（正则 `_TIME`，仅支持 `09:00-17:00` 单时段），带来源/置信度/14 天 TTL/过期降级 UNKNOWN，官方来源（`OFFICIAL_ATTRACTION`/`OFFICIAL_TOURISM`）+ 已审核时可标记 `hard_constraint_eligible`。
- City Intelligence 已解析高德 v5 `place/text` 的 `business.opentime_today/opentime_week`，但以**自由文本**进入 `TIMING`（1 天 TTL）/`ATTRACTION`（30 天 TTL）事实。
- POI 搜索主路径（`providers/map.py` 的 `_AmapPoi`）**丢弃**高德 `business` 字段（`extra="ignore"` 未映射）。
- Planner 当前**不使用**营业时间做时间窗约束：唯一的营业相关硬过滤是 `TEMPORARY_CLOSURE`（仅官方+新鲜+已审核）；`OPENING_HOURS_APPLIED` 只是 impact 记录，不存在实际窗口核验。
- Hard Validation Phase 1（`detect_hard_constraint_violations`）只覆盖预算/日期/固定安排/重复 POI/活动重叠，**无营业时间规则**；`feasible` 在 completed 事件中恒为 `true`（不可行走 planning-failed 事件）。
- 关键语义缺口：`停止入场`、`周一闭馆`、多时段、跨午夜、24 小时、旺季/淡季、节假日**均无法被当前抽取器结构化理解**；`opening_hours` 字段类型是自由文本 `str`。

**Verdict：NEEDS_DATA_FOUNDATION（附带 2 个产品决策点）。**
Validator 设计合理、contract 可承载，但数据层尚未达到"高可信营业时间→硬校验"的输入标准。直接实现 validator 会制造假安全（把自由文本当结构化时间比较），违背 Correctness over coverage 原则。

## 3. Provider Capability

### 3.1 AMap

| 问题 | 结论 |
| --- | --- |
| 是否返回营业时间 | 是。高德 v5 `place/text` 的 POI 响应含 `business` 对象（`opentime_today`、`opentime_week`、`cost`），当前仅 `city_intelligence.py:67-70` 解析 |
| 当前 Provider 是否解析 | 部分。POI 搜索主路径 `_AmapPoi`（`providers/map.py:185`）**未映射 `business`**，`extra="ignore"` 丢弃；City Intelligence 路径解析了 `opentime_today/opentime_week` 但只以文本 statement 进入事实 |
| 是否丢弃 | 是（POI 搜索路径丢弃；City Intelligence 路径以文本保留） |
| 是否只保留 raw payload | 否——`Poi` 模型是清洗后的；原始 JSON 不持久化（缓存 `_CachedPoiSearch` 只存 `Poi` 元组） |
| 结构化程度 | `opentime_today` 形如 `"09:00-17:00"` 或 `"全天开放"`/`"休息"`，未做进一步解析 |

**结论**：AMap 有原始营业时间文本能力，但当前主链路丢弃、辅助链路降级为自由文本。

### 3.2 Guide Intelligence

- 攻略抽取存在营业时间：`_TIME` 正则（`trusted_facts.py:88`）匹配 `\d{1,2}:\d{2}\s*[-—至到]\s*\d{1,2}:\d{2}`，生成 `OPENING_HOURS` candidate，`normalized_value={"openTime","closeTime"}`。
- 是 **半结构化事实**：`OPENING_HOURS` 有 `statement`（原始句）+ `normalized_value`（结构化 openTime/closeTime）+ `evidence` + `confidence` + `checked_at`/`expires_at` + `effective_date`。
- 有 source（`source_name`/`source_url`/`source_type`）、confidence、TTL（`_TTL_BY_CATEGORY["OPENING_HOURS"]=14 天`）、evidence。
- 结构化模型抽取器（`structured_model.py` `HttpStructuredModelTransport`，可接 LLM）同样输出 `TrustedFactCategory`（含 OPENING_HOURS），走同一 `FactValidator` 管道。
- **局限**：`_TIME` 只取第一个配对；`停止入场`（`16:30 停止入场`）不解析；`周一闭馆`/`每周二闭馆`不解析；多时段 `09:00-12:00;14:00-17:00` 只取 `09:00-12:00`；跨午夜 `20:00-02:00` 会被 `_validate_opening` 判为 `OPENING_HOURS_REVERSED` 而拒绝。

### 3.3 City Intelligence

- 提供**POI 级营业文本**（高德 `business.opentime_*`），但以城市情报批量方式采集（前 8 个 POI），生成 `TIMING`（1 天 TTL，confidence 0.8）与 `ATTRACTION`（30 天 TTL，confidence 0.86）自由文本事实。
- **不要把城市级知识误认为 POI opening hours**：`TIMING`/`ATTRACTION` fact 的 statement 是"营业信息…"文本，没有结构化 `openTime/closeTime`，不可直接用于窗口比较。

### 3.4 Knowledge assets

- `knowledge/guangzhou/*.md` **不含营业时间**；文档明示"页面未提供…实时开放状态和预约信息"、"实时开放时间、闭馆日…出发前再次核验"。即知识资产明确**不承诺**营业时间（防止陈旧知识当入场承诺）。
- `knowledge/sources/guangzhou.toml`：source registry，`reliability_level=OFFICIAL`、`fetch_interval_hours=168`——freshness 模型存在。

### 3.5 Demo Provider

- `DemoMapProvider` 生成合成 POI，**无营业时间**（属性固定），`estimated=True`。Demo 模式天然 UNKNOWN。

## 5. Reliability / Freshness

### 5.1 事实来源优先级（现状已内建）

```
OFFICIAL_ATTRACTION / OFFICIAL_TOURISM（reviewed 后 hard_constraint_eligible）
  > MAP_PROVIDER（高德 business，未结构化）
  > PUBLIC_GUIDE（社区攻略，soft signal）
  > COMMUNITY（小红书等，soft signal）
  > UNKNOWN（无数据）
```

- `hard_constraint_eligible` 规则（`worker/contracts.py:293-298`）：stale 不得硬约束；硬约束必须 `source_reviewed` + 官方可靠性。
- 冲突处理：`PlanningContextConflict`（selected/conflict/downgraded_fact_ids）存在，但**营业时间专属冲突决策未实现**（无"同 POI 两来源营业时间冲突时选择哪个"逻辑）。
- **缺口**：无 source precedence 合并规则用于 OPENING_HOURS 冲突；当前 `FactMerger` 合并策略需核查（见 Open Decisions）。

### 5.2 Freshness（现状）

| 事实 | TTL | 说明 |
| --- | --- | --- |
| `OPENING_HOURS` | 14 天 | `_TTL_BY_CATEGORY` |
| `TEMPORARY_CLOSURE` | 6 小时 | 高时效 |
| `TIMING`（高德营业文本） | 1 天 | City Intelligence |
| `ATTRACTION` | 30 天 | City Intelligence |
| Knowledge source 采集 | 168 小时 | `sources/*.toml` |

- `FactValue.at(checked_at)`：过期自动返回 UNKNOWN（不硬删，可追溯）。
- **"营业时间多久算 stale"无业务依据**：14 天是现有工程常量。若需校准 → `NEEDS_CALIBRATION`（不拍脑袋写 7/30 天）。
- 模型已支持 `retrieved_at`（=fetched_at/checked_at）、`effective_date`、`expires_at`（freshness 三要素齐备）。

## 6. Time Semantics

| 概念 | 现状 |
| --- | --- |
| Itinerary timezone | `CHINA_TIME_ZONE`（Asia/Shanghai，`domain/shared.py`）；`ItineraryActivity.startTime/endTime` 为 tz-aware ISO datetime |
| Day 内排程 | `DayPlanItem.start_minute/end_minute`：日窗口（默认 9:00–18:00）内分钟偏移 |
| Provider 时间 | 高德 `opentime_*` 文本无显式时区（隐式本地时间） |
| LocalDate | 行程日期为 `date`；`planning_fact_impacts` 按 `effective_date` 匹配 |
| UTC 转换 | facts 的 `checked_at`/`expires_at` 强制 tz-aware（`FactProvenance.__post_init__`）；`evaluated_at` 强制 tz-aware |
| 跨午夜 | **不支持**（`_validate_opening` 将 close<=open 判为 REVERSED 拒绝） |
| 多日 | `effective_date` 支持单日事实；无多日营业区间概念 |

**结论**：活动时间与事实时间都是 Asia/Shanghai tz-aware，**基础时区一致**；但跨午夜营业（如夜市 `20:00-02:00`）当前被拒绝，且没有任何字符串→时间的"显式比较"（`_TIME` 仅抽取，无比较逻辑）。设计必须禁止字符串直接比较，统一走 `time` 解析 + tz 语义。

| 结构化开闭窗口 | 无（`opening_hours` 是 `str`） | ❌ |
| last entry | 无 | ❌ |
| 多时段 / 周内模式 / 节假日 | 无 | ❌ |
| timezone 归属 | `FactProvenance.fetched_at` tz-aware | ✅ |

### 7.2 建议的收敛模型（新增，不改 schema）

沿用 `FactValue` 风格，新增一个**归一化值**（reuse `normalized_value: dict` 承载，避免新表）：

```python
OpeningHoursWindow = {
  "weekday": 0..6 | None,          # None=每日
  "intervals": [{"open": "09:00", "close": "17:00"}, ...],  # 多时段
  "last_entry": "16:00" | None,    # 停止入场
  "closed": False,                 # 当日闭馆
  "note": "旺季/淡季不同" | None,   # 无法结构化的保留文本
}
```

- 归一化值挂到 `PlanningContextFact.normalized_value`（已存在字段，dict，schema 已允许 `JsonValue`），**不新增 contract 字段**。
- 评估并收敛状态为（满足三分类语义即可）：
  - `KNOWN_VALID`（窗口内且时长足够）
  - `KNOWN_INVALID`（闭馆 / 窗口外 / 时长不足 / last-entry 违反）
  - `UNKNOWN`（无数据 / stale / conflicting 未决）
- 显式 `last_entry_time` 作为**可选独立字段**（区分 closing_time），因为中国景点普遍"16:00 停止入场 / 17:00 闭馆"。

## 8. Validation Semantics

### 8.1 Evidence State（评估后收敛）

| 状态 | 定义 | 硬校验结果 |
| --- | --- | --- |
| `VERIFIED_WINDOW` | 高可信（官方/已审核）窗口，`[start, end]` 完全落入且时长≥min | PASS |
| `VERIFIED_CLOSED` | 高可信当日闭馆 | HARD FAIL |
| `OUTSIDE_WINDOW` | 高可信窗口，但计划时间在窗口外 | HARD FAIL |
| `INSUFFICIENT_DURATION` | 窗口剩余 < minDuration | HARD FAIL |
| `LAST_ENTRY_VIOLATION` | 进入时间 ≥ last_entry | HARD FAIL |
| `UNKNOWN` | 无数据 | 不 fail，标记 unverified |
| `STALE` | 有过期事实 | diagnostic/warning，不 fail |
| `CONFLICTING` | 多来源冲突 | diagnostic / repair trigger，不 fail |

### 8.2 Entry vs Visit Feasibility（必须都检查）

- **Entry**：`start_time < closing_time` 且 `start_time < last_entry_time`（若有）。
- **Visit**：`start_time + minDuration <= closing_time`（且整段可落入某个 interval）。

例：`09:00-17:00`，16:50 到达，min 2h → Entry 通过但 Visit 失败 → `INSUFFICIENT_DURATION`。

### 8.3 minDuration 判定

- 使用 `DurationProfile.min_minutes`（`poi_quality.py`，NORMAL=90）。
- 可用窗口 `< minDuration` → HARD FAIL（默认倾向，符合 §10 推荐）。窗口数据是 UNKNOWN 时**不**适用此条（避免假安全）。

## 9. UNKNOWN Semantics

**推荐（产品决策点 P1，本设计采用）：**

- UNKNOWN opening hours **不导致 hard fail**；
- itinerary 可继续完成；`feasible` 不因此变 false；
- 但 validation diagnostics 标记 `UNVERIFIED`（对应现有 `EvaluationWarning` 或未来 diagnostic 通道），并在 `factImpacts`/解释中说明"无法验证营业时间"。
- 与现有 `hard_closed_fact` 逻辑一致：只有**已审核官方**事实才允许阻止安排（`docs/archive/27-product-completeness…`：只有经过授权 Provider 提供的营业/闭馆/预约类事实才阻止规划安排）。

**当前模型支持度**：`EvaluationWarning`（INFO/WARNING/CRITICAL）可表达"未验证"提示；`feasible` 恒 true 的模型天然满足"UNKNOWN 不 fail"。**架构缺口**：暂无独立"diagnostic"通道区分"已知软问题"与"unverified"（可用新 WarningCode 或放宽 code 枚举承载）。

## 10. Hard Validation Issue Taxonomy（Proposal）

| code | 语义 | 分类 |
| --- | --- | --- |
| `POI_CLOSED_ON_DATE` | 当日闭馆（含周闭馆/特定日） | HARD |
| `POI_OUTSIDE_OPENING_HOURS` | 计划窗口在营业窗口外 | HARD |
| `POI_INSUFFICIENT_OPEN_WINDOW` | 剩余窗口 < minDuration | HARD |
| `POI_LAST_ENTRY_VIOLATION` | 进入时间 ≥ last_entry | HARD |
| `POI_OPENING_HOURS_UNKNOWN` | 无数据可验证 | DIAGNOSTIC |
| `POI_OPENING_HOURS_STALE` | 事实过期 | DIAGNOSTIC/WARNING |
| `POI_OPENING_HOURS_CONFLICT` | 多来源冲突 | DIAGNOSTIC / repair trigger |
| `FIXED_SCHEDULE_OUTSIDE_OPENING_HOURS` | 用户固定安排 vs 现实约束 | HARD（复用 `POI_OUTSIDE_OPENING_HOURS` + `constraintRefs` 亦可，待决策 P3） |

- 实现策略：**不全部实现**。优先 HARD 四类；DIAGNOSTIC 三类复用 warning 通道；`FIXED_SCHEDULE_*` 建议复用 code + constraint 引用。
- 现有 schema：`evaluationWarning.code` 是 enum → 新增 code 需 `planning-completed-event` schema 变更（v8→v9 或放宽 `enum`）。这是**有意的、最小的 contract impact**，不是 Phase 2A 阻断项。

## 11. Validator Boundary

现状（Phase 1，已验证）：

```
Itinerary ─→ PlanEvaluator.evaluate ─→ detect_hard_constraint_violations ─→ 违规则 raise DATA_QUALITY_ERROR（planning-failed）
                                                         │
                                                         └→ 通过则 PlanEvaluation(feasible=True, warnings)
```

- **Validator 只 Detect 不 Mutate** ✅（`evaluator.py` 头部明示 side-effect-free；`rules.py` 全部为纯函数）。
- 违规表达为 `PlanningProviderError(DATA_QUALITY_ERROR)`，由 worker 转 `PLANNING_FAILED` 事件（`worker/processor.py:211-214`）；用户获失败 → replan 链路（`replan_service.py` `LocalReplanningProvider`）。
- **结论**：边界已遵循推荐结构；Phase 2A 的 validator 直接追加到 `detect_hard_constraint_violations` 同级即可，无需重构。

## 12. Planner Integration

现状：Planner 除 `hard_closed_fact`（官方临时闭馆过滤）外**不消费营业时间**；`OPENING_HOURS_APPLIED` 仅为解释性 impact（`trusted_context.py:132-143`），无窗口约束效果。

| Option | 描述 | 评估 |
| --- | --- | --- |
| A. 只做最终 Hard Validation | 改动最小 | 大量 plan→fail→repair；且数据层未就绪 |
| B. Placement 前约束 + Final Validation | 正确架构 | 需 CandidateActivity 带 opening window，改动大 |
| **C. 分阶段**（推荐） | Phase 2A1: Final Validator；Phase 2A2: Planner availability integration | **采纳**；符合本阶段"先数据基础后消费"的顺序 |

- Phase 2A1（数据归一化 + Final Validator）先落地：数据来自 `normalized_value` 与高德 business 归一化。
- Phase 2A2（Planner availability）：`CandidateActivity` 增加可选 `opening_windows`，`plan_day` 在窗口外惩罚/跳过候选；作为排序信号而非硬约束先行。

## 13. Repair / Replan

- **Validator 不负责选择 repair**：只输出 issue（POI、date、planned time、opening interval、available duration、required min、source、confidence）。
- Repair 策略候选（由 Repair/Replan engine 负责）：
  1. 前移/后移 activity 使其落入窗口；
  2. 缩短至 ≥ minDuration（仍需 Visit 可行）；
  3. 与同日 activity swap；
  4. 移到其他日期；
  5. replacement candidate；
  6. 最终 hard fail（`PlanningInfeasibleError` → `PLANNING_INFEASIBLE` / `NO_FEASIBLE_ITINERARY`）。
- 现状 replan：`LocalReplanningProvider` 按天重排，可复用作 repair 载体；失败最终以 `PlanningInfeasibleError` 上报。

---

## 14. Fixed / Must Visit Interaction

- **Fixed Schedule vs 现实约束**：现实约束优先。`FIXED_SCHEDULE_OUTSIDE_OPENING_HOURS` 输出不可行解释（code 复用或新增，待 P3），纳入 `detect_hard_constraint_violations` 同级检查。
- **Must Visit 当日闭馆**：不能静默删。沿用现有 `closure_unplaced` 逻辑（`planning_provider.py:357-379`）扩展：`POI_CLOSED_ON_DATE` 时 Repair 尝试其他日期；所有行程日期均不可行 → `PlanningInfeasibleError`，解释 `must-visit cannot be scheduled within opening hours`（沿用 `MUST_VISIT_UNAVAILABLE` conflict code 语义）。
- **ActivityKind 范围**：默认仅 `ATTRACTION`、`EXPERIENCE` 检查；`MEAL`（餐厅营业时间）未来可支持但本阶段不纳入；`ACCOMMODATION`（check-in hours 语义不同）、`ARRIVAL`/`DEPARTURE` 不适用。当前模型天然支持（`kind` 已入 schema）。

## 15. Contract / Persistence / Web Impact

链路审计：Python `completion event v8` → Java `PlanningCompletedEvent`/`PlanningCompletedEventParser` → DB → API → Web。

| 层 | 现状 | Phase 2A 影响 |
| --- | --- | --- |
| Python `PlanningContextFact` | `normalized_value: dict` 已允许 `JsonValue` | 可挂结构化营业时间，**无需改 contract** |
| Python `PlanEvaluation` | `feasible=Literal[True]`、warnings enum | 新增 warning code 需 schema 变更 |
| Messaging `planning-completed-event-v8.schema.json` | `additionalProperties:false` + `evaluationWarning.code` enum | 新 code → **最小 contract impact**（v8→v9 或放宽 enum） |
| Java `PlanningCompletedEvent.java` | 已解析 `PlanEvaluation`/`EvaluationWarning` | 新 code 字符串透传即可（Java 侧用 `Set<String>` 校验白名单，需同步加） |
| `PlanningCompletedEventParser.java:27-38` | `EVALUATION_WARNING_CODES`/`SEVERITIES`/`ENTITY_TYPES`/`REASON_CODES` 白名单 | 需同步扩展（低成本） |
| DB / API / Web | 消费 warnings/decisions 通用结构 | 新 code 透传，无结构变化 |

**结论**：generic validation issue 已可透传；新增 opening-hours issue **不是** schema 结构性变更，而是 enum/白名单的增量扩展 → `MINIMAL_CONTRACT_CHANGE_REQUIRED`（非 `NO_CONTRACT_CHANGE_REQUIRED`，因 warning code 是闭集）。

## 18. Recommended Architecture

```
高德 v5 place/text business.opentime_*  ─┐
Guide OPENING_HOURS fact (normalized)   ─┼→ OpeningHoursNormalizer → normalized_value(intervals/last_entry/closed/note)
City Intelligence TIMING fact           ─┘                                  │

                                                                           │
                    ┌──────────────────────────────────────────────────────┼──────────────┐

        Phase 2A1: Final Hard Validator                     Phase 2A2: Planner availability      Web/诊断
```

## 22. Verdict

**NEEDS_DATA_FOUNDATION（附带产品决策点 P1/P2/P4）**

理由：
1. **有可信数据来源**：高德 `business.opentime_*`（v5）、guide `OPENING_HOURS` facts（官方+reviewed 后可硬约束）——管道已存在；
2. **数据可映射到 POI**：`Attraction.opening_hours`、`_entity_facts_for_pois` 已把 facts 投影到候选；canonical POI identity 已稳定；
3. **时间语义**：活动与事实均 Asia/Shanghai tz-aware，基础一致；但跨午夜/多时段/last_entry 语义缺失；
4. **validator contract 足够**：`detect_hard_constraint_violations` 扩展点就绪，warning/failed 双通道可承载；
5. **UNKNOWN 不会误判为 OPEN**：`FactValue`/`stale`/`hard_constraint_eligible` 机制成熟，官方门槛防假安全；
6. **但数据层不足**：`opening_hours` 是自由文本 `str`；`停止入场`/`周一闭馆`/多时段不可解析；POI 搜索路径丢弃高德 `business`；Planner 不消费窗口——必须先完成 B1/B2/B4（数据归一化 + domain model + 高德字段恢复）才能让 Validator 有可靠输入。

**不选 DEFER**：数据管道与信任机制已存在，补齐是确定性的工程工作而非研究空白；直接实现 validator 才是 DEFER 的理由（假安全）。

**下一步（Phase 2B 候选）**：按 B1→B4→B3 顺序实施数据基础，再上 validator；全程不改 Evaluation 封板内容（rule-v3 不动，新增独立 opening-hours 校验点）。
